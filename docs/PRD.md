# PRD — 평택대 축제 부스 QR 주문·결제 시스템

> 소유자: 팀장 | 상태: 승인 | 최종 수정: 2026-09-22
> 상태는 초안/승인 두 가지. "승인"으로 바꾸는 것은 팀장만 한다 — 승인 전 구현 착수 금지.

## 한 줄 정의

축제 부스 고객이 QR로 접속해 로그인 없이 메뉴·옵션·수량을 골라 현금 또는 송금(은행 계좌이체·카카오페이 개인 송금·토스 개인 송금)으로 주문하고, 운영진이 실시간 대시보드에서 입금 확인·조리·완료를 처리하며 재고와 매출을 관리하는 웹 서비스.

## 배경 / 문제

- 학과 차원의 대동제(2026-10-07~08) 부스 1개 운영. 수기 주문·현금 계산은 대기 줄·주문 누락·매출 집계 오류를 낳는다.
- 사업자 등록이 불가하므로 PG 가맹 결제(토스페이먼츠·네이버페이·카카오페이 가맹)는 쓸 수 없다 → 결제수단은 현금·송금(개인 송금 QR/링크 방식: 은행 계좌이체·카카오페이 개인 송금·토스 개인 송금)으로 한정하고, 입금 확인은 관리자 수동 승인으로 한다. 시스템은 "주문 접수 + 결제 확인 + 상태 관리 + 재고·매출 집계"를 담당한다. 자동 입금 확인(오픈뱅킹 API)은 계약 절차 때문에 제외.
- 개발 마감 2026-10-04(1차), 2026-10-05~06(2차). 팀장 제외 5~6명(프론트 1~2, 디자인 1~2, 백엔드 2~3, DB 1~2). 팀 숙련도: 자바 하, 프론트 중 → TypeScript 풀스택으로 통일.
- 예상 규모: 부스 1개, 주문 약 200건/일, QR 5개 이하(부스 앞 및 축제 곳곳).
- 이 문서는 팀원(개발자)이 각자 AI 도구로 구현할 때의 기준 문서다.

## 사용자

| 사용자 유형 | 핵심 니즈 |
|---|---|
| 고객 (축제 방문객, 외국인 유학생 포함) | 로그인·동의 절차 없이 최소 단계로 주문하고, 픽업 번호와 진행 상태를 확인한다. 한국어/영어 선택. |
| 운영진 (부스 관리자, 계정 2~3개) | 새 주문을 놓치지 않고 확인하고, 은행·카카오페이·토스 앱에서 입금을 확인하거나 현금 수령을 확인해 결제확인 처리하고, 조리·완료 상태를 바꾸고, 품절·재고·매출을 관리한다. 단순한 UI. |
| 팀장 (비개발) | 축제 후 매출·통계 CSV로 정산한다. |

## 요구사항

우선순위 표기: 필수(1차, ~10-04) / 필수-2차(10-05~06) / 제외(미구현 — F-38) / 4차(이번 프로젝트 범위 밖, 일정 미정 — F-39). F-35~F-41은 2026-09-22 필수-2차로 승격됐다가, 같은 날 F-38은 미구현·F-39는 4차로 재조정됨.

### 기능 요구사항

| ID | 요구사항 | 우선순위 (필수/권장/보류) | 승인 기준 (검증 가능한 조건 — Given-When-Then 권장) |
|---|---|---|---|
| F-01 | QR 진입 메뉴판: QR의 URL로 접속하면 로그인 없이 메뉴 목록(이름·가격·품절 여부·이미지 유무 무관)이 표시된다 | 필수 | Given 메뉴 3개 중 1개가 품절, When 고객이 QR URL로 접속, Then 로그인 없이 메뉴 3개가 보이고 품절 메뉴는 "품절" 표시와 함께 선택 불가 |
| F-02 | 수량 선택: 메뉴별 수량을 1 이상으로 조절할 수 있다 (상한은 해당 메뉴의 현재 재고) | 필수 | Given 재고 5인 메뉴, When 수량 6 입력, Then 5로 제한되거나 오류 안내. When 수량 0 이하 입력, Then 담기 불가 |
| F-03 | 옵션 선택: 메뉴별로 정의된 옵션(예: 견과류 유/무, 시즈닝 종류, 설탕 양 단계)을 선택할 수 있다. 옵션 정의는 데이터로 관리(코드 하드코딩 금지). 옵션마다 추가 가격을 가질 수 있다(0원 포함) — 구체 값은 메뉴 확정 후 시드 데이터로 입력 (Open Question #14 답변) | 필수 | Given 옵션 그룹 "설탕 양"(선택지 3개, 그중 1개 추가 가격 500원) 있는 메뉴, When 고객이 선택지 하나 선택 후 담기, Then 장바구니 항목에 선택한 옵션명과 추가 가격이 표시되고 주문 생성 시 서버에 옵션 ID로 전달되며 서버 합계에 추가 가격이 포함됨. 추가 가격 0원 옵션은 합계 변화 없음 |
| F-04 | 장바구니: 여러 메뉴·옵션·수량 조합을 담고 수정·삭제하고 합계를 본다 | 필수 | Given 항목 2개 담김, When 하나 삭제, Then 합계가 남은 항목 기준으로 재계산. Given 빈 장바구니, Then 주문 버튼 비활성 + 빈 상태 안내 |
| F-05 | 다국어: 고객 화면의 UI 문자열·메뉴명·옵션명을 한국어/영어로 전환할 수 있다. 언어 추가가 가능한 데이터 구조 | 필수 | Given 언어 en 선택, When 메뉴판 로드, Then UI 문자열·메뉴명·옵션명 전부 영어. 번역 누락 시 한국어로 폴백(빈 문자열 노출 0건). 새 언어 코드 추가 시 코드 변경 없이 데이터 행 추가만으로 가능 |
| F-06 | 결제수단 선택: 주문 확정 전에 현금 / 송금 중 하나를 고른다. 송금을 고르면 하위 수단(은행 계좌이체 / 카카오페이 개인 송금 / 토스 개인 송금) 중 하나를 고른다. PG 가맹 결제는 없음. 선택한 결제수단·송금 하위 수단은 주문에 기록되어 통계·CSV에 포함된다 | 필수 | Given 장바구니 비어 있지 않음, When 결제수단 미선택(또는 송금 선택 후 하위 수단 미선택)으로 확정 시도, Then 주문 생성 안 됨. When 송금 + 카카오페이 선택 후 확정, Then 주문 레코드에 결제수단=송금, 하위 수단=카카오페이 저장. 현금 선택 시 하위 수단 없음 |
| F-07 | 주문 생성: 서버가 메뉴 ID·옵션 ID·수량만 받아 가격·합계를 재계산하고, 주문·주문항목 생성·재고 차감을 하나의 DB 트랜잭션으로 처리한다. 클라이언트가 보낸 가격 값은 무시 | 필수 | Given 클라이언트가 합계 0원으로 조작한 요청, When 주문 생성, Then 서버 계산 합계로 저장. Given 재고 1인 메뉴에 동시 주문 2건, Then 1건만 성공하고 재고는 0(음수 없음). 실패 시 주문·항목·재고 모두 롤백 |
| F-08 | 중복 주문 방지(멱등키): 주문 화면 진입 시 클라이언트가 UUID 멱등키를 생성해 전송하고, 같은 키의 재요청은 새 주문을 만들지 않고 기존 주문을 반환한다 | 필수 | Given 동일 멱등키로 주문 요청 2회(새로고침·재전송 포함), Then 주문 1건만 존재하고 두 응답 모두 같은 주문 ID·픽업 번호. 재고는 1회만 차감 |
| F-09 | 픽업 번호: 주문 생성 시 일련번호 픽업 번호를 부여해 주문 완료 화면에 크게 표시한다. 번호는 축제 전체(10-07~08) 연속 번호이며 날짜별 리셋이 없다 (Open Question #13 답변, 2026-09-22 수정) | 필수 | Given 주문 생성 성공, Then 화면에 픽업 번호 표시. 축제 전체에서 같은 번호가 두 주문에 부여되지 않음. Given 10-07 마지막 번호 150, When 10-08 첫 주문, Then 픽업 번호 151 |
| F-10 | 주문 상태 확인 페이지: 주문 완료 화면에서 이동 가능한 URL로 현재 상태(결제대기/결제확인/조리중/완료/취소/환불/만료)를 확인한다. 로그인 없음. URL에는 주문 생성 시 서버가 발급한 추측 불가 토큰이 포함되며, 픽업 번호만으로는 조회할 수 없다 (Open Question #20 답변 — 메인 세션 추천값. 근거: 고객이 이 페이지에서 취소 요청(F-45)·송금 신고(F-43)를 하므로 타인이 픽업 번호를 추측해 남의 주문을 조작하면 안 됨) | 필수 | Given 관리자가 상태를 조리중으로 변경, When 고객이 상태 페이지 열람(또는 새로고침), Then "조리중" 표시. 존재하지 않는 주문 URL → "주문을 찾을 수 없음" 안내. Given 픽업 번호만 아는 제3자, When 픽업 번호로 URL을 구성해 접근, Then 조회 불가(토큰 없이는 404 동등 응답). 토큰 형식·길이는 팀장 확정(추측 불가 조건: 무작위 128비트 이상 권장 — 추정) |
| F-11 | 현재 대기인원: 고객 화면(메뉴판·상태 페이지)에 "내 앞의 미완료 주문 수"를 표시한다. 정의: 내 주문보다 먼저 생성된 주문 중 아직 완료·취소·환불·만료가 아닌 것(결제대기·결제확인·조리중)의 수 (Open Question #10 답변, 2026-09-22 수정 — 사용자 원문은 "(조리중)"이라 적었으나 결제대기·결제확인 포함은 메인 세션 해석). 메뉴판(주문 전)에서는 "내 주문"이 없으므로 현재 전체 미완료 주문 수를 표시한다(해석) | 필수 | Given 내 주문보다 먼저 생성된 주문이 결제대기 1건·결제확인 2건·조리중 1건·완료 5건, 내 주문 뒤에 생성된 조리중 2건, Then 내 상태 페이지에 대기 4건 표시(뒤 주문 2건은 제외). 0건이면 "대기 없음". 완료·취소·환불·만료는 제외. Given 메뉴판(주문 전), Then 전체 미완료 주문 수 표시 |
| F-12 | 개인정보 고지: **1차** — 수집하는 개인정보가 없음을 고지하고, 주문 데이터 파기 시점을 명시한다. 별도 동의 클릭 단계 없음. 파기 시점 = 축제 종료(2026-10-08) 후 한 달 = 2026-11-08 (Open Question #6 답변; N-15와 동일값). **2차 조건부 확장(2026-09-22, Open Question #29 부분 답변 — 사용자 원문 "필요의 경우 전화번호를 받는 것도 좋아")** — 전화번호를 수집하는 2차 기능(F-39 배달 등) 착수 시: 해당 기능의 주문 흐름에만 수집 동의 체크(수집 항목=전화번호, 이용 목적, 파기 시점 2026-11-08)를 추가하고 고지문에 수집 항목·파기 시점을 갱신한다. 전화번호를 수집하지 않는 주문 흐름(픽업)은 계속 동의 단계 0개. 최초 인터뷰 원문 "개인정보 수집 동의(문자 시 전화번호, 그 외의 기본적인 동의서, 이후 파기 시점 명시)"가 근거 | 필수 (조건부 확장은 필수-2차) | 1차: Given 고객 화면 어디서든, Then 고지 문구(수집 항목 없음 + 파기 시점 "2026-11-08")에 1탭 이내 접근 가능. 주문 흐름 중 동의 체크 단계 0개. 2차(전화번호 수집 기능 착수 시): Given 배달 주문 흐름에서 전화번호 입력, When 동의 체크 없이 확정 시도, Then 주문 생성 안 됨 + 동의 필요 안내. When 동의 체크 후 확정, Then 주문에 동의 시각 기록. Given 픽업 주문 흐름, Then 동의 체크 단계 0개(1차와 동일). 고지문에 "수집 항목: 전화번호(배달 주문 시)·파기 2026-11-08" 표시 |

## 범위 제외 (이번에 하지 않는 것)

- PG 가맹 결제(토스페이먼츠·네이버페이·카카오페이 가맹 결제) — 사업자 등록 불가. 개인 송금 링크(카카오페이 송금코드·토스 송금 링크)는 가맹 결제가 아니므로 포함(F-42)
- 자동 입금 확인(금융결제원 오픈뱅킹 API 등) — 계약 절차 필요. 입금 확인은 관리자 수동(F-15)
- 주문별 결제 QR 생성 — 고객이 이미 웹 화면에 있으므로 불필요. 송금 안내는 버튼·링크로 제공(F-42)
- 문자(SMS) 알림 — 제외 유지. 대안: 픽업 번호 화면 + 상태 페이지 URL. (2026-09-22 갱신) 2차 배달(F-39)에서 전화번호 수집이 허용됐지만 이 결정은 SMS 알림 도입이 아니다 — SMS 알림 도입 여부는 별도 확인(Open Question #33)
- 재료(BOM) 단위 재고 — 메뉴 단위 재고로 대체
- NFC 오더
- 테이블 오더(테이블 번호 기반 주문)
- QR 코드 매일 교체 — 도메인 인쇄 + 육안 확인으로 대체 (N-11)
- 고객 로그인·회원가입
- 개인정보 수집·동의 절차 — **1차 범위에서만 제외**(수집 항목 없음). (2026-09-22 갱신) 2차 전화번호 수집 기능(F-39 배달) 착수 시 동의 체크(F-12 2차)·암호화(N-17)·파기(N-15)가 범위에 들어온다 — 사용자 원문 "필요의 경우 전화번호를 받는 것도 좋아"
- 도메인 구매 — Vercel 기본 도메인 사용 (N-14)
- 관리자 회원가입 화면 — Supabase 대시보드 수동 생성 (F-20)
- 메뉴 신규 등록·삭제 UI는 1차 범위 제외 — 2차(F-46)
- 송금 주문의 시간 기반 자동 만료 중 송금 신고된 건 — 만료 없이 관리자 판단 (F-17)
- 조리중 주문의 고객 환불 요청 버튼 — 불가(Open Question #23 답변). 조리중 환불은 부스 구두 요청 → 관리자 재량(F-19)
- (2026-09-22 갱신) 부가기능 F-35~F-41은 보류에서 필수-2차로 승격됨(Open Question #19 답변). 단, 각 항목의 "세부 미정" 사항(Open Question #25~#31, #33)은 착수 전 사용자 확인 필요 — 확인 전 해당 세부는 구현하지 않음
