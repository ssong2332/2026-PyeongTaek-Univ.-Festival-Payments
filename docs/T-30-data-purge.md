# T-30 주문 데이터 파기 절차 초안 (DB2)

상태: 선작업 초안 — 운영 실행용 확정본 아님.
담당: 김 혁(DB2). 문서 완성 목표 2026-10-04, 실제 파기·확인 2026-11-08.

기준: `origin/dev` 250bc9a의 PRD F-12·N-15, Architecture,
`0001_schema.sql`·`0003_rls.sql`, ADR-0009.
담당 배정은 [T-30 노션 카드](https://app.notion.com/p/T-30-3e3cf8e440ef8102862bd6699007fb00)의
2026-09-24 DB2 이관 내용을 따른다. 현재 dev Tasks의 DB1 파기 담당 표기는
노션과 다르므로 최종 검수 시 팀장이 정합성을 확인한다.

## 범위

이번 선작업은 대상 목록과 절차를 정리한다. DB 스키마·API·시드를 변경하지
않고, 운영 DB에 접속하거나 데이터를 삭제하지 않는다. 실행 SQL의 예정 경로는
`supabase/scripts/purge_2026-11-08.sql`이며, 이 초안에는 실행 SQL을 포함하지 않는다.
파기 방법은 PRD N-15에 따라 팀장이 확정하며 아래는 스크립트 방식의 제안이다.

## 현재 스키마의 파기 대상

| 테이블 | 포함 데이터 | 현재 외래키 관계 |
|---|---|---|
| `orders` | 모든 상태의 주문, 상태 토큰·멱등키, 결제·송금 신고·취소 요청 정보 | 주문의 부모 |
| `order_items` | 주문 당시 메뉴·가격·수량 스냅샷 | `orders` 삭제 시 CASCADE |
| `order_item_options` | 주문 당시 옵션명·가격 스냅샷 | `order_items` 삭제 시 CASCADE |
| `order_status_history` | 상태 변경·주체·사유 기록 | `orders` 삭제 시 CASCADE |

대상은 이번 축제 주문 전체(현금·계좌이체, 완료·취소·환불·만료·미처리 포함)다.
테스트·수기 입력 주문도 누락하지 않는다. 실행 전 다른 행사 데이터가 같은
DB에 섞였는지 확인하고, 섞였으면 전체 삭제하지 말고 식별 기준을 먼저 확정한다.
단순 생성 날짜만으로 이번 축제 주문이라고 단정하지 않는다.

현재 FK 기준으로 부모 주문 삭제 시 위 세 자식 테이블도 삭제된다. 메뉴·옵션으로
향하는 FK는 주문 스냅샷 삭제가 메뉴 원본 삭제를 유발하지 않는다. 후속 마이그레이션
적용 후 FK와 DELETE 트리거를 다시 확인해야 한다. 무제한 `TRUNCATE ... CASCADE`로
미확인 테이블까지 삭제하는 방식은 사용하지 않는다.

## 보존 대상으로 제안하는 데이터

| 대상 | 보존 이유 |
|---|---|
| `menu_items`, `menu_item_translations` | 메뉴 원본과 번역. 재고·품절·활성 상태도 그대로 유지 |
| `option_groups`, `option_group_translations`, `options`, `option_translations` | 메뉴 옵션 원본과 번역 |
| `app_settings` | 운영 설정. 파기 스크립트에서 초기화하지 않음 |
| `counters` | 발급 이력과 무관하게 카운터를 임의로 0으로 되돌리지 않음 |
| Supabase Auth 관리자 계정 | 주문 데이터가 아님. 계정 정리는 DB1의 별도 운영 절차 |
| 스키마·함수·정책·마이그레이션 이력 | 데이터 파기에서 구조를 변경하지 않음 |

계좌 설정·관리자 계정 자체의 행사 종료 후 정리 정책은 팀장·해당 담당자가
별도로 확정한다. 이 표는 영구 보관을 승인하는 의미가 아니다.

## 후속 작업이 생기면 추가 확인할 대상

- T-51 `rate_limits`: ADR-0009에 파기 대상으로 명시되어 있다. 현재 기준
  마이그레이션에는 없으므로 생성 후 실제 구조·FK를 확인하고 정리 단계에 포함한다.
- T-41 후기 테이블: 주문 연결·후기 내용·별점의 파기 범위를 최종 스키마와 함께 확정한다.
- 통계·리포트: 원본 주문의 사본을 저장하는 테이블·파일이 추가되면 함께 조사한다.
- T-49 전화번호·동의 기록: 현재는 프로젝트 범위 밖이다. 실제 도입되면
  암호화 값과 동의 기록을 모두 대상에 추가하고 잔여 값 0건을 검증한다.
- CSV·PDF 다운로드, 백업·로그·외부 저장 파일은 DB DELETE만으로 없어지지 않는다.
  보유 위치·담당자·보존 종료 및 삭제 방법을 확인하고 DB 파기 결과와 구분하여 기록한다.

## 실행 절차 제안

### 1. 실행 전 (10-04까지 준비, 11-08 실행 직전 재확인)

1. 최종 마이그레이션 목록·FK·트리거·저장된 집계·내보낸 파일을 재검토한다.
2. 대상 Supabase 프로젝트 식별자, 실행자(DB2), 검수자, 실행 시각(KST)을 확정한다.
   문서·PR에는 DB 비밀번호·서비스 키·계좌 값·주문 토큰을 기록하지 않는다.
3. 2026-11-08 이전에는 운영 삭제를 실행하지 않는다. 정확한 실행 시각은 팀장이 정한다.
4. 팀장이 대상 범위와 파기 방법을 확인한 뒤 주문 생성·수기 입력·스윕 등 쓰기 경로를
   중단하는 방법을 배포 담당과 확인한다. 중단 확인 전 실행하지 않는다.
5. 삭제 전 대상별 건수와 보존 대상의 상태를 확인한다. 민감한 원문 대신 건수·검증
   결과만 기록한다. 새 원본 백업을 임의로 만들어 파기 기한을 연장하지 않는다.
6. 검토된 SQL 버전과 실제 스키마가 일치하고 독립 DB 테스트가 통과했는지 확인한다.

### 2. 삭제 및 확인 (11-08)

1. 확정된 삭제 SQL을 트랜잭션 안에서 실행한다. 오류 또는 예상치 못한 범위 발견 시
   커밋하지 않고 롤백한다. 미확인 FK를 우회하려고 제약이나 트리거를 끄지 않는다.
2. 같은 트랜잭션에서 대상 주문·항목·옵션·이력이 0건인지 확인한다.
   후속 데이터가 포함되면 그 검증도 함께 수행한다.
3. 메뉴·재고·설정·카운터 등 보존 대상이 변경되지 않았는지 확인한 뒤 커밋한다.
4. 별도 조회로 커밋 후 잔여 건수를 다시 확인한다. 이후 쓰기 경로를 실수로 재개해
   주문을 재생성하지 않도록 서비스 종료 상태를 배포 담당과 확인한다.
5. 커밋 이후 오류는 롤백으로 되돌릴 수 없으므로, 발생 시 임의 복원 대신 팀장에게
   보고하고 복원이 파기 정책에 미치는 영향을 검토한다.

### 3. 완료 기록

실행 일시(KST), 프로젝트 식별자, SQL 커밋, 실행자·검수자, 테이블별 전후 건수,
보존 검증 결과, 실패·재시도 여부, 파일·백업·로그 정리 결과와 남은 항목을 기록한다.
주문 원문·토큰·연락처를 실행 증빙으로 붙이지 않는다. 이주노 DoD 1차 점검 후
팀장이 최종 상태를 판정한다.

## 독립 DB 테스트 계획

- 여러 결제수단·상태의 주문과 각 자식 레코드를 만들고 전부 삭제되는지 확인.
- 메뉴·옵션·번역·재고·설정·카운터를 실행 전후 비교하여 보존되는지 확인.
- 주문 0건에서 실행 성공, 두 번 실행해도 보존 데이터가 동일한지 확인.
- 삭제 도중 의도적으로 실패시켜 주문과 자식 레코드가 모두 롤백되는지 확인.
- 잘못된 프로젝트·실행일·미확정 대상이면 실제 삭제 전에 중단하는 장치 검증.
- T-53 이후 스키마 및 후기·속도 제한 등 최종 추가 테이블을 포함하여 재검증.

운영 DB를 테스트에 사용하지 않는다. 현재는 문서만 작성했으며 위 테스트는 미실행이다.

## 완료 전 확정할 항목

- 팀장: 삭제 방식, 행사 데이터 범위, 실행 시각, 보존 대상 승인.
- DB1: T-03·T-53 및 추가 스키마 확정, 실제 FK·트리거와 파기 영향 확인.
- 배포 담당: T-25 이후 프로젝트 식별 및 쓰기 중단·서비스 종료 방법.
- DB2: 실제 SQL 작성, 독립 DB 검증, 11-08 실행·결과 기록.
- QA: 전체 운영 문서와 이 문서의 연결 및 체크리스트 검수.

T-25나 최종 스키마가 확정되기 전에는 이 초안을 운영 실행 준비 완료로 표시하지 않는다.
