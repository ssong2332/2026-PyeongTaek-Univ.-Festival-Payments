# T-30 주문 데이터 파기 절차 및 SQL 초안 (DB2)

상태: **Draft · 운영 실행 보류**. 2026-11-08 파기 예정일 경과, 완료 미확인·잔여 데이터 확인. 새 승인일·실행일 미정.
담당: 김 혁(DB2). 실행 여부와 범위는 팀장이 DB1 검증 결과를 받아 별도로 결정한다.

기준: 2026-11-11 `dev`의 PRD F-12·N-15, Architecture, `0001_schema.sql`부터
`0105_create_admin_menu.sql`까지의 적용 가능한 전체 마이그레이션, DECISIONS #30·#36, ADR-0009.
담당 배정은 [T-30 노션 카드](https://app.notion.com/p/T-30-3e3cf8e440ef8102862bd6699007fb00)의
2026-09-24 DB2 이관 및 PR #28(2026-09-24 결정)에 따라 DB2 전담으로 확정한다.

## 범위

이번 선작업은 대상 목록·절차와 [실행 SQL 초안](../supabase/scripts/purge_2026-11-08.sql)을 정리한다.
DB 스키마·API·시드를 변경하지 않는다. 이 PR은 운영 DB 파기를 실행하지 않는다.
PR 병합과 운영 파기 승인·실행은 별도 결정이다. 파기 방법과 운영 적용은 PRD N-15에 따라 팀장이 최종 확정한다.

## 2026-11-11 운영 현황과 미확인 사항

14:57 KST 검토자가 연결된 축제 Supabase 프로젝트에서 SELECT·메타데이터 조회만으로 확인한 값이다.
이 PR 작업에서 운영 DB를 다시 조회하거나 변경하지 않았다.

| 대상 | 잔여 건수 |
|---|---:|
| `orders` | 187 |
| `order_items` | 241 |
| `order_item_options` | 21 |
| `order_status_history` | 705 |
| `reviews` | 1 |
| `staff_calls` | 1 |
| `rate_limits` | 1 |
| `shifts` (이름 포함) | 67 |
| `pickup_number` 카운터 | 186 |

주문 생성 시각은 2026-10-07~11-07(UTC)이며 11-08 KST 이후 새 주문은 0건이라는 조회 결과다.
현재 잔여 건수로는 파기 완료 조건(대상 0건)을 충족하지 않는다. 11-08 당일 실제
파기 시도·실행 여부는 이 조회만으로 알 수 없으므로 실행 이력과 인수인계 자료를 확인해야 한다.
운영 마이그레이션은 0105까지 적용된 것으로 보고됐다. 주문 직접 참조 FK 네 개는
`order_items`, `order_status_history`, `reviews`, `staff_calls`이다.
트리거·추가 저장처·다른 행사 데이터 혼재 여부는 별도 검증 전까지 미확인이다.

## 현재 스키마의 파기 대상

| 테이블 | 포함 데이터 | 현재 외래키 관계 |
|---|---|---|
| `orders` | 모든 상태·결제수단·수기 입력(`0104`) 주문, 상태 토큰·멱등키, 결제·송금 신고·취소 요청 정보 | 주문의 부모 |
| `order_items` | 주문 당시 메뉴·가격·수량 스냅샷 | `orders` 삭제 시 CASCADE |
| `order_item_options` | 주문 당시 옵션명·가격 스냅샷 | `order_items` 삭제 시 CASCADE |
| `order_status_history` | 상태 변경·주체·사유 기록 | `orders` 삭제 시 CASCADE |
| `reviews` (`0102`) | 완료 주문 후기·별점 | `orders` 삭제 시 CASCADE |
| `staff_calls` (`0103`) | 주문 연결 직원 호출·확인 기록 | `orders` 삭제 시 CASCADE |
| `rate_limits` (`0018`) | 주문 생성 IP 해시별 속도 제한 기록 | 주문 FK 없음. ADR-0009·DECISIONS #36에 따라 명시적으로 파기 |

대상은 이번 축제 주문 전체(현금·계좌이체, 완료·취소·환불·만료·미처리 포함)다.
테스트·수기 입력 주문도 누락하지 않는다. 실행 전 다른 행사 데이터가 같은
DB에 섞였는지 확인하고, 섞였으면 전체 삭제하지 말고 식별 기준을 먼저 확정한다.
단순 생성 날짜만으로 이번 축제 주문이라고 단정하지 않는다.

현재 FK 기준으로 주문을 직접 참조하는 네 테이블과 `order_items`를 참조하는
`order_item_options`는 모두 명시적 파기 대상이다.
메뉴·옵션으로 향하는 FK는 주문 스냅샷 파기가 메뉴 원본 삭제를 유발하지 않는다.
SQL은 이 테이블들을 `TRUNCATE ... RESTRICT`로 한 번에 지운다. 새 FK가 생기면
실패하도록 `CASCADE`를 붙이지 않는다. 실제 실행 직전 최종 FK·트리거를 다시 확인한다.

## 보존 대상으로 제안하는 데이터

| 대상 | 보존 이유 |
|---|---|
| `menu_items`, `menu_item_translations` | 메뉴 원본과 번역. 재고·품절·활성 상태도 그대로 유지 |
| `option_groups`, `option_group_translations`, `options`, `option_translations` | 메뉴 옵션 원본과 번역 |
| `app_settings` | 운영 설정. 파기 스크립트에서 초기화하지 않음 |
| `counters`의 다른 키 | 유지. `pickup_number` 값만 DECISIONS #30에 따라 0으로 초기화 |
| `shifts` (`0100`) | 주문과 직접 연결되지 않은 교대 기록. `person_name`은 식별 가능 데이터이며 보존·파기 정책 미확정. 현재 SQL은 삭제하지 않음 |
| Supabase Auth 관리자 계정 | 주문 데이터가 아님. 계정 정리는 DB1의 별도 운영 절차 |
| 스키마·함수·정책·마이그레이션 이력 | 데이터 파기에서 구조를 변경하지 않음 |

계좌 설정·관리자 계정·근무자 이름의 행사 종료 후 정리 정책은 팀장·DB1과 해당
담당자가 별도로 확정한다. 이 표는 영구 보관을 승인하는 의미가 아니다.

## 후속 작업이 생기면 추가 확인할 대상

- 후속 테이블: 0104·0105 이후에도 주문 FK나 개인 정보가 추가되면 파기 범위·검증 쿼리에 포함한다.
- 재고 사진 기능이 도입되면 Storage 파일뿐 아니라 촬영자 메타데이터의 보존·파기 기준을 결정한다.
- 통계·리포트: 원본 주문의 사본을 저장하는 테이블·파일이 추가되면 함께 조사한다.
- T-49 전화번호·동의 기록: 현재는 프로젝트 범위 밖이다. 실제 도입되면
  암호화 값과 동의 기록을 모두 대상에 추가하고 잔여 값 0건을 검증한다.
- CSV·PDF 다운로드, 백업·로그·외부 저장 파일은 DB DELETE만으로 없어지지 않는다.
  보유 위치·담당자·보존 종료 및 삭제 방법을 확인하고 DB 파기 결과와 구분하여 기록한다.

## 실행 절차 제안

### 1. 별도 운영 실행 승인 전 체크포인트 (새 실행일 미정)

1. 11-08 파기 실행 이력·인수인계 자료를 확인하고, 현재 187건이 남은 경위를 기록한다.
   실제 주문 데이터를 전부 삭제해도 되는지, 테스트·사후 개발에 필요한 데이터가
   있는지 팀장이 판단한다. 다른 행사 주문이 같은 DB에 섞였는지 확인하기 전에는
   전체 `TRUNCATE`를 실행하지 않는다.
2. 팀장·DB1이 `shifts.person_name`, 이후 도입될 재고 사진 촬영자, CSV·PDF 다운로드,
   백업·로그·외부 파일의 보유 위치와 보존·파기 기준을 확정한다.
3. 운영 프로젝트 식별자(ref), 실행자, 독립 검수자, 새 실행 시각(KST), 검토된 SQL
   커밋을 사전 기록한다. 프로젝트 식별자는 Supabase 대시보드와 연결 정보에서
   교차 확인한다. 문서·PR에는 비밀번호·서비스 키·계좌 값·주문 토큰을 기록하지 않는다.
4. DB1이 운영 마이그레이션 이력·FK·트리거·추가 저장처와 격리 DB 테스트 결과를
   대조한다. 대상 테이블별 최종 건수·다른 행사 혼재 여부·보존 대상 상태를
   실행자와 검수자가 함께 기록한다. 민감한 원문은 증빙으로 남기지 않는다.
5. 주문 생성·수기 입력·스윕 등 모든 쓰기 경로를 중단할 방법을 배포 담당이 확인하고,
   실행 직전에 중단 상태를 검수자가 재확인한다. 새 원본 백업을 임의로 만들어
   파기 기한을 연장하지 않는다.
6. 위 항목을 문서화한 뒤 **팀장에게 운영 파기 별도 승인**을 받는다. SQL의
   2026-11-08 날짜 가드와 `pickup_number` 존재 확인은 이 승인·프로젝트 확인을
   대신하지 않는다. 승인 전에는 Draft·병합·운영 실행 보류를 유지한다.

실행 전에 아래 기록을 별도 운영 문서에 채우고 실행자·검수자가 대조한다. 빈칸이
있거나 값이 일치하지 않으면 SQL Editor에 파일을 붙여 넣지 않는다.

| 사전 체크포인트 | 기록할 값 |
|---|---|
| 11-08 실행 이력·잔여 187건 조사 | 확인 자료, 담당자, 결론 |
| 대상 프로젝트 | Supabase 프로젝트 ref, 대시보드·연결 정보 대조 결과 |
| 대상 행사 범위 | 다른 행사 주문 혼재 여부, 전체 삭제 가능 판정 |
| 파기·보존 정책 | 주문·`shifts.person_name`·재고 사진·CSV/백업·로그 각각의 결정 |
| 최종 스키마 | 마이그레이션 이력, FK·트리거·추가 저장처 확인 결과 |
| 실행 전 건수 | 대상 테이블 7개와 `pickup_number`, 보존 대상 건수 |
| 쓰기 중단 | 주문 생성·수기 입력·스윕 등 중단 확인 시각 |
| 실행 통제 | SQL 커밋, 새 실행일(KST), 실행자, 독립 검수자, 팀장 승인 기록 |

### 2. 승인된 날짜의 삭제 및 확인

1. 확정된 SQL 파일 전체를 Supabase SQL Editor에서 한 번에 실행한다. 오류 또는 예상치
   못한 범위 발견 시 커밋하지 않고 롤백한다. 미확인 FK를 우회하려고 `CASCADE`를
   붙이거나 제약·트리거를 끄지 않는다.
2. 같은 트랜잭션에서 대상 주문·항목·옵션·이력·후기·직원 호출·속도 제한이 0건인지
   확인한다. `pickup_number` 카운터만 0으로 초기화한다.
3. 메뉴·재고·설정·다른 카운터 등 보존 대상이 변경되지 않았는지 확인한 뒤 커밋한다.
4. 별도 조회로 커밋 후 잔여 건수를 다시 확인한다. 이후 쓰기 경로를 실수로 재개해
   주문을 재생성하지 않도록 서비스 종료 상태를 배포 담당과 확인한다.
5. 커밋 이후 오류는 롤백으로 되돌릴 수 없으므로, 발생 시 임의 복원 대신 팀장에게
   보고하고 복원이 파기 정책에 미치는 영향을 검토한다.

### 3. 완료 기록

실행 일시(KST), 프로젝트 식별자, SQL 커밋, 실행자·검수자, 테이블별 전후 건수,
보존 검증 결과, 실패·재시도 여부, 파일·백업·로그 정리 결과와 남은 항목을 기록한다.
주문 원문·토큰·연락처를 실행 증빙으로 붙이지 않는다. 이주노 DoD 1차 점검 후
팀장이 최종 상태를 판정한다.

## 격리된 로컬 Supabase DB 테스트 계획

- 번호순 전체 마이그레이션(현재 0001~0105의 실제 파일 전부)을 CI의
  disposable 로컬 Supabase DB에 적용한다.
- 현금·계좌이체, 7개 주문 상태, `0104.create_manual_order`로 만든 수기 주문 두 건과
  자식 레코드(`reviews`, `staff_calls` 포함)를 만들고 전부 삭제되는지 확인한다.
- 메뉴·옵션·번역·재고·설정·다른 카운터와 `shifts.person_name` fixture가
  실행 전후 유지되는지 확인한다. 이름 보존은 현재 SQL의 동작 검증이며 정책 승인이 아니다.
- 주문 0건에서 실행 성공, 두 번 실행해도 보존 데이터가 동일한지 확인.
- 삭제 도중 의도적으로 실패시켜 주문과 자식 레코드가 모두 롤백되는지 확인.
- 격리 DB 접속 주소 가드와 실행 전 승인 체크포인트를 확인한다.
- 추가 테이블이 생기면 새 FK에서 파기가 멈추는지 재검증한다.

운영 DB를 테스트에 사용하지 않는다. CI에서만 로컬 disposable Supabase DB를
`supabase db reset --local --no-seed`로 초기화해 전체 마이그레이션 이력을 확인한 뒤
`tests/integration/purge_2026-11-08.sh`의 fixture·파기 검증을 실행한다. `0019_pg_cron`은
Supabase가 설정한 `postgres` DB에서만 설치되므로 별도 CREATE DATABASE에 적용할 수 없다.
현재는 날짜 가드가 이미 지났으므로
운영 SQL 원문 그대로 격리 DB에서 파기·보존·재실행·새 FK 차단·롤백을 검증한다.
운영 DB 적용 전에는 실제 프로젝트·데이터 범위·최종 스키마를 다시 검증한다.

## 완료 전 확정할 항목

- 팀장: 주문 전체 삭제 가능 여부, 다른 행사 데이터 혼재, 근무자·복제본 보존 정책,
  새 실행일과 실행자·검수자 승인.
- DB1: 운영 DB의 0105까지 이력과 최종 FK·트리거·추가 저장처 확인.
  미적용·다른 스키마라면 SQL을 그대로 실행하지 않는다.
- 배포 담당: 프로젝트 식별 및 쓰기 중단·서비스 종료 방법.
- DB2: SQL 초안 작성, 격리 DB 검증, 승인 후 실행·결과 기록.
- QA: 전체 운영 문서와 이 문서의 연결 및 체크리스트 검수.

위 승인·최종 스키마·실행 이력 확인 전에는 이 초안을 운영 실행 준비 완료로 표시하지 않는다.
