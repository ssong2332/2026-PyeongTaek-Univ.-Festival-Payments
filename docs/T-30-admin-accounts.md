# T-30 관리자 계정 생성 절차 초안 (DB1)

상태: 선작업 초안 — 운영 URL과 실제 계정 준비 여부는 T-25(배포) 후 확정한다.
담당: 서동혁(DB1). 문서 완성 목표 2026-10-04.

기준: PRD F-20·Open Question #17(관리자 계정은 Supabase 대시보드에서 수동 생성, 앱 내 회원가입 없음),
Architecture "배포 전 필수 설정"(이메일 회원가입 비활성화, 관리자 계정 2~3개), `0003_rls.sql`.

## 왜 회원가입 차단이 가장 중요한가

현재 설계는 **로그인한(authenticated) 계정을 모두 관리자로 본다**(`0003_rls.sql` 주석, Architecture 3절).
authenticated 역할은 주문·주문 항목·상태 이력·설정을 읽을 수 있다. 따라서 Supabase의 이메일 회원가입이
열려 있으면, 앱에 가입 화면이 없어도 누구나 Auth API로 계정을 만들어 주문 데이터를 볼 수 있다.
**계정을 만들기 전에 반드시 1단계를 먼저 끝내고 확인한다.**

로컬 개발 환경은 `supabase/config.toml`의 `[auth] enable_signup = false`로 이미 막혀 있다.
이 설정은 로컬에만 적용되므로 **운영 프로젝트는 대시보드에서 따로 꺼야 한다.**

## 절차

Supabase 대시보드의 메뉴 이름은 버전에 따라 조금 다를 수 있다. 설정 이름("Allow new users to sign up",
"Auto Confirm User")은 Supabase 공식 문서·토론 기준으로 확인했고(2026-09-25), 화면 위치는 주소로도 적어 둔다.
실제 작업 때 화면과 다르면 이 문서를 고친다.

### 1. 이메일 회원가입 끄기 (T-25 배포 전)

1. Supabase 대시보드에서 운영 프로젝트(`2026-PyeongTaek-Univ.-Fe…`)를 연다.
2. **Authentication → Sign In / Providers**로 이동한다(주소가 `…/dashboard/project/<프로젝트 ID>/auth/providers`인 화면).
3. **Allow new users to sign up**(신규 사용자 가입 허용)을 끄고 저장한다. 화면에 없으면 Authentication의 다른
   설정 화면에서 같은 이름의 스위치를 찾는다(공식 문서의 대시보드 경로는 `…/auth`).
4. **Email** 제공자는 켜 둔다. 이메일+비밀번호 로그인에 필요하다. 다른 소셜 로그인 제공자는 켜지 않는다.

확인 방법(배포 담당 또는 DB1): 운영 프로젝트의 anon 키로 가입을 시도해 거부되는지 본다.
키 값은 문서·채팅에 붙이지 않고 터미널에서만 쓴다.

```bash
curl -s -X POST "$SUPABASE_URL/auth/v1/signup" \
  -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: application/json" \
  -d '{"email":"signup-check@example.com","password":"CheckOnly-12345"}'
# 기대 결과: "Signups not allowed" 류의 오류. 계정이 만들어지면 즉시 1단계를 다시 확인하고 그 계정을 삭제한다.
```

### 2. 관리자 계정 만들기 (2~3개, F-20)

1. **Authentication → Users → Add user → Create new user**를 누른다.
2. 이메일과 비밀번호를 입력하고 **Auto Confirm User**를 체크한다. 호스팅 Supabase는 기본으로 이메일 확인(Confirm email)을
   요구하므로, 체크하지 않으면 확인 메일을 누르기 전까지 로그인이 안 된다. 비밀번호는 기본값이 없으니 직접 정해 입력한다.
3. 운영진 **한 사람당 한 계정**을 만든다. 계정을 돌려 쓰지 않는다.
   - 입금 확인·상태 전환 기록(`orders.acknowledged_by`, `order_status_history.actor_id`)에 계정 ID가 남는다.
     계정을 나눠야 누가 처리했는지 추적할 수 있다.
4. 비밀번호 규칙(제안): 12자 이상, 다른 서비스와 같은 비밀번호 금지, 이메일·이름·학번이 들어간 비밀번호 금지.

### 3. 비밀번호 전달과 기록

- 비밀번호는 **본인에게 1:1로만** 전달한다. 단톡방·노션·GitHub(이슈·PR·문서)에 쓰지 않는다.
- 계정 목록은 **이름과 이메일만** 기록한다(보관 위치는 팀장이 정함). 비밀번호는 기록하지 않는다.
- 받은 사람은 첫 로그인 전에 비밀번호를 본인만 아는 값으로 바꾸기를 권장한다.
  (앱 안에 비밀번호 변경 화면은 없으므로, 필요하면 DB1이 대시보드에서 새 비밀번호로 재설정해 1:1로 다시 전달한다.)

### 4. 로그인 확인 (T-25 후)

운영 URL(`https://<T-25에서 확정>.workers.dev`)에서 각 계정으로 확인한다.

| 확인 | 기대 결과 |
|---|---|
| 로그인하지 않고 `/admin` 접속 | `/admin/login`으로 이동(F-20) |
| 올바른 이메일·비밀번호로 로그인 | 대시보드 표시 |
| 틀린 비밀번호 | 오류 문구, 대시보드 진입 안 됨 |
| 로그인 화면 | 회원가입 링크·버튼 없음 |

모든 계정이 확인되면 아래 "준비 현황"을 채운다.

### 5. 분실·교체·퇴출

- **비밀번호 분실:** Authentication → Users에서 해당 사용자를 열어 새 비밀번호로 재설정하고 1:1로 전달한다.
- **담당자 교체·퇴출:** 해당 사용자를 삭제(또는 비밀번호 재설정)하고 새 계정을 만든다.
  기존 주문 기록의 `acknowledged_by`·`actor_id`는 외래키가 없는 UUID라 계정을 지워도 주문 기록은 남는다.
- **유출 의심:** 즉시 해당 계정 비밀번호를 재설정하고 팀장에게 알린다. 다른 계정도 필요하면 재설정한다.

### 6. 축제 종료 후 정리 (제안 — 팀장 확정 필요)

- 운영 종료(10-08) 직후: 모든 관리자 계정 비밀번호를 재설정해 운영 기간 비밀번호를 무효화한다.
- 계정 삭제 시점은 주문 데이터 파기일(2026-11-08, [파기 절차](T-30-data-purge.md))과 맞추는 것을 제안한다.
  파기 절차 문서는 관리자 계정을 파기 대상이 아닌 별도 정리 대상으로 두었다.
