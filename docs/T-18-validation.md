## 검증 대상 (Architecture `POST /api/admin/sweep` · ADR-0006, PRD F-17·F-43)

- 호출 경로: `sweepOrders(repository)`(`src/services/sweepService.ts`) → `SupabaseSweepRepository.sweep()` → DB 함수 `sweep_order_timeouts()` → 건별 `transition_order(pending → expired, 'expire', 'system')`
- Route Handler(`src/app/api/admin/sweep/route.ts`)는 `requireAdmin()` 뒤 위 조합을 그대로 부른다. 통합 테스트는 mock을 쓰지 않으므로(DECISIONS #46) 서비스부터 실제 저장소·실제 DB로 직접 호출했다.

## 남은 것

- **자동 만료 실행 경로**: 대시보드 30초 호출(`useSweepHeartbeat`)은 PR #112로 dev에 병합됐다 — 관리자 대시보드가 열려 있는 동안만 동작한다. 상시 실행인 pg_cron(0019)은 PR #82 Draft(김 혁). 스윕 성공 건수·실패 원인 로그와 운영 문서의 점검 절차는 PR #113으로 병합됐다. 30초 호출의 화면 동작과 운영 DB pg_cron 실행 확인은 이 PR 범위가 아니다.
- 통합 테스트는 파일을 하나씩 순서대로 돌리고(`fileParallelism: false`) 테스트마다 만든 주문을 지운다. 스윕은 DB 전체를 대상으로 하므로 초기화된 DB를 전제로 한다. 알려진 한계:
  - 사전조건 검사는 **현재 설정 기준**으로만 본다. 설정을 5분으로 줄이는 테스트는 "5분 넘고 현재 기준에는 못 미친" 결제대기 주문이 남아 있으면 그 주문까지 만료시키고 건수가 어긋난다(로컬 확인).
  - 설정 복원 테스트는 늘린 설정이 상한(120분)을 넘지 않아야 하므로, DB의 `payment.expire_minutes`가 111분 이상이면 그 1개가 실패한다(로컬 확인 — 기본값 10분·CI에는 해당 없음).
- 자동 완료(T-19, `auto_complete.enabled`)는 이 검증 범위가 아니다 — 설정이 꺼진 상태(`completed: 0`)만 확인했다.
- 운영 DB의 pg_cron 실행 이력, 로그인을 포함한 화면 흐름(T-24 E2E)은 각 작업에서 확인한다.
