## 1. 종이 메뉴판·현금 수기 주문

### 1.1 전환 조건 및 준비물

- 고객 QR 접속 불가, 주문 생성 실패, 관리자 대시보드 장애 등 정상적인 주문 처리가 어려우면 운영 책임자에게 즉시 보고한다.
- 온라인 접수 중단 및 수기 전환은 현장 책임자가 결정한다. 장애 발생·전환 시각과 마지막 정상 주문번호를 기록한다.
- 종이 메뉴판(확정된 가격), 수기 주문 기록지, 필기구, 현금 보관함·거스름돈, 임시 주문번호표, 조리 전달 전표를 준비한다.
- 고객에게 시스템 점검에 따른 **현금 수기 주문** 전환을 안내한다. 임의의 계좌번호·비공식 QR·송금 링크를 안내하지 않는다.

### 1.2 접수·조리·전달 절차

1. 메뉴·옵션·수량과 총금액을 고객과 확인한다.
2. 임시 번호를 `M-001`, `M-002`처럼 부여하여 온라인 픽업 번호와 구별한다. 이 번호 체계는 현장 책임자가 운영 전에 최종 승인한다.
3. 수기 기록지에 접수 시각, 임시 번호, 주문 상세, 총금액, 받은 현금, 거스름돈을 적는다.
4. 현금 수령을 확인한 뒤 고객에게 번호를 알려 주고 동일 번호를 적은 전표를 조리 담당자에게 전달한다.
5. 조리 완료 후 번호로 호출하고 전달 완료 시각을 기록한다.
6. 취소·환불 시 기존 기록을 지우지 않고 사유·반환 금액·담당자를 별도로 기록한다.

수기 기록의 기본 항목: 임시 주문번호 / 접수 시각 / 메뉴·옵션·수량 / 총금액 / 수령액 / 거스름돈 / 결제수단 / 상태(접수·조리중·전달완료·취소) / 담당자 / 비고. 고객의 이름·전화번호는 수집하지 않는다.

### 1.3 재고·매출과 복구 후 처리

- 수기 판매 수량 및 현금 매출은 온라인 데이터와 분리해 기록한다.
- 복구 직전 온라인에서 접수된 주문의 실제 저장·결제 여부를 먼저 대조한다. 오류 화면만 보고 주문 실패로 단정하거나 재생성하지 않는다.
- 수기 주문 사후 입력(**T-28**)은 2026-10-06 운영 배포됐다(#137·#98, 2차 릴리스 #144). 복구 뒤 관리자가 기록지를 보고 입력한다.
  - 화면 주소: `https://ptu-festival-payments.aiisgod.workers.dev/admin/manual-orders` — **관리자 화면 메뉴에 이 화면으로 가는 링크가 없다.** 주소를 직접 열거나 운영 전에 관리자 기기에 즐겨찾기한다. 관리자 로그인이 필요하다.
  - 입력: M 번호는 숫자만(`M-001` → `1`, 필수), 종이에 적힌 **접수 시각** 그대로, 메뉴·옵션·수량, 결제수단. 접수 시각은 지난 시각만 저장된다 — 미래 시각이나 빈 칸이면 저장 버튼이 꺼지고 이유는 표시되지 않는다.
  - 재고가 모자라도 저장되고 재고는 0에서 멈춘다(화면 경고). 같은 M 번호를 다시 넣으면 "이미 사용 중" 안내가 뜨고 저장되지 않는다.
  - 저장 뒤 완료 주문 목록에 `M-001`·"수기 입력"으로 보이는지 확인한다. 매출·통계·CSV 날짜는 입력한 시각이 아니라 종이 접수 시각 기준이다(DECISIONS #62).
  - 사후 입력이 안 되면 기록지를 보존하고 별도 정산한다.
- 온라인·수기 주문 및 재고·매출 중복 반영 여부를 운영 책임자와 함께 확인하고 정상 운영을 재개한다.

## 2. QR 코드 육안 점검 및 위변조 대응

- QR 인쇄물 하단에 T-25 배포 확인을 거친 **공식 운영 URL**(`https://ptu-festival-payments.aiisgod.workers.dev` — 맨 위 운영 URL 줄)을 함께 인쇄한다. 옛 주소(`asg21274`)와 임시 테스트 URL은 사용하지 않는다.
- 운영 시작 전, 담당자 교대 시, 운영 중 매시간(제안 주기), 이상 신고 즉시 점검한다. 최종 점검 주기는 현장 책임자가 확정한다.
- 인쇄물이 원위치에 있는지, 다른 스티커가 덧붙었거나 훼손되지 않았는지 확인한다.
- 스마트폰으로 QR을 인식해 표시되는 주소와 인쇄된 공식 URL을 비교하고 정상 주문 페이지 접속을 확인한다.
- 주소 불일치 또는 위변조 의심 시 해당 QR의 사용을 즉시 중단·가리고, 발견 시각과 인쇄물·연결 주소를 기록한 뒤 책임자에게 보고한다. 검증된 예비 인쇄물로 교체하고 두 명이 재확인한다.
- 의심스러운 페이지에 개인정보·관리자 계정 정보를 입력하지 않는다. 이미 해당 QR을 이용한 고객이 있다면 피해 여부를 확인할 수 있도록 별도 사고 기록을 남긴다.

점검 기록 항목: 점검 시각 / 담당자 / 인쇄물 상태 / URL 일치 여부 / 접속 결과 / 이상 및 조치 / 정상화 시각.

## 3. 서비스 장애 및 비상 연락 체계

### 3.1 장애 유형

고객 주문 화면 오류, 관리자 로그인·대시보드 오류, 현장 네트워크 장애, API·DB 오류, 입금 내역 확인 불가, QR 위변조 의심 등을 구분하여 기록한다. 연결 장애 시 가능하다면 모바일 데이터 등 다른 네트워크에서 접속을 비교한다.

### 3.2 대응 순서

1. **발견:** 발생 시각·증상·화면·마지막 정상 주문번호를 기록한다. 주문 확정 직후 오류가 났다면 동일 주문을 즉시 재접수하지 않는다.
2. **보고:** 현장 운영 책임자에게 알려 신규 온라인 주문의 일시 중단 및 수기 전환 여부를 결정받는다.
3. **진단:** 배포·백엔드 담당자가 Cloudflare Workers·API를, DB 담당자가 Supabase·주문 저장 여부를, 프론트엔드 담당자가 화면을 확인한다. QA 담당자는 재현과 복구 검증을 기록한다.
4. **폴백:** 장애가 지속되면 현장 책임자 승인 아래 1절의 현금 수기 주문으로 전환한다. 전환 시각을 공유한다.
5. **복구:** 고객 메뉴·주문 생성·관리자 수신·결제 확인·상태 변경을 점검하고 온라인/수기·결제 미확인 주문을 대조한 뒤 책임자 승인으로 재개한다.

### 3.3 연락 명단 — 운영 전 확정

| 순서 | 역할 | 책임 | 실제 담당자·연락 수단 |
|---|---|---|---|
| 1 | 현장 운영 책임자 및 대체 책임자 | 운영 중단·수기 전환·재개 결정 | 운영 전 입력 |
| 2 | 공동팀장 / QA | 사고 기록·복구 검증 | 운영 전 입력 |
| 3 | 백엔드·배포 담당 | API·Worker·배포 점검 | 운영 전 입력 |
| 4 | DB 담당 | Supabase·주문 저장 여부 확인 | 운영 전 입력 |
| 5 | 프론트엔드 담당 | 고객·관리자 화면 확인 | 운영 전 입력 |

전화번호와 개인 연락처는 공개 저장소에 커밋하지 말고 운영진만 접근할 수 있는 별도 연락망에 보관한다.

### 3.4 미확인 주문 및 사고 기록

- 결제 확인이 불가능하면 입금 확인·조리 시작으로 임의 전환하지 않는다. 은행 앱의 실제 입금 내역과 주문을 대조한다.
- 온라인 주문과 `M-` 수기 주문은 별개로 관리해 중복 조리·지급·재고 차감을 방지한다.
- 발생 시각 / 최초 발견자 / 장애 유형·증상 / 영향 범위 / 마지막 정상 주문번호 / 주문 중단·수기 전환 시각 / 연락·조치 내용 / 복구 검증 및 재개 시각 / 잔여 미확인 주문을 기록한다.

### 3.5 미입금 주문 자동 만료·자동 완료 점검

- 운영 전 실제 활성화된 스윕 호출 경로를 확인한다. 선택지는 DB의 1분 `pg_cron` 작업(#82)과 관리자 대시보드가 열린 동안의 30초 heartbeat(#112)다. PR 상태만 보고 운영에 적용됐다고 판단하지 않는다.
- 관리자 화면에서 미입금 주문이 만료되지 않으면 먼저 `order.sweep` 로그의 `expired`·`completed` 건수와 `order.sweep.rpc_failed`·`order.sweep.rpc_threw`·`order.sweep.invalid_result` 오류 이벤트를 확인한다. 오류 로그의 `code`는 진단 코드이며 DB 오류 원문이나 설정값은 기록하지 않는다. `INVALID_PAYMENT_EXPIRE_MINUTES`·`INVALID_AUTO_COMPLETE_ENABLED`·`INVALID_AUTO_COMPLETE_MINUTES`는 해당 설정 키를 점검하라는 뜻이다.
- 로그가 전혀 없다면 호출 경로가 활성화됐는지 확인한다. `pg_cron` 사용 시 DB 담당자가 `cron.job` 등록과 `cron.job_run_details` 최근 실행 결과를 확인한다. heartbeat만 사용 중이면 관리자 대시보드 접속이 유지되는지 확인한다.
- 설정값 오류 코드가 의심되면 DB 담당자가 `app_settings`의 `payment.expire_minutes`(정수 1~120), `auto_complete.enabled`(`true`/`false`), `auto_complete.minutes`(자동 완료 사용 시 정수 1~120)를 확인한다. 잘못된 값이 있으면 만료와 자동 완료가 함께 멈출 수 있다. 운영 설정은 관리자 설정 화면으로 수정하고, Table Editor 직접 수정은 담당자와 변경 이력을 확인한 뒤에만 진행한다.
- 복구 후 스윕이 다시 실행되는지, 만료 대상·송금 신고 제외·재고 복구·상태 이력을 대조한다. 이미 만료되거나 전환된 주문을 임의로 재생성하지 않는다.

## 4. 관리자 설정 화면 장애 시 Supabase 폴백

운영 계좌의 입력·변경 순서, 값 규칙, 확인 방법은
[T-30 운영 계좌(송금 정보) 입력 절차](T-30-transfer-settings.md)를 단일 기준으로 사용한다.

이 매뉴얼에서는 해당 내용을 중복 기재하지 않으며,
실제 계좌 값은 GitHub·Notion·단체 채팅·운영 기록에 남기지 않는다.

### 4.1 적용 및 승인

- 기본 변경 경로는 T-52 관리자 설정 패널이다.
- 관리자 설정 화면만 사용할 수 없고 Supabase DB는 정상인 경우에만 Table Editor 폴백을 사용한다.
- 운영 계좌 3개(`transfer.*`)의 실제 값 입력·변경은 **DB1(서동혁)**이 Supabase Table Editor에서 수행한다(2026-10-02 DECISIONS #55로 팀장에서 변경).
  실제 값은 **팀장(박수홍)**이 DB1에게 1:1로 전달한다.
- DB1은 입력 후 [T-30 운영 계좌 입력 절차](T-30-transfer-settings.md)의 3단계 확인 쿼리로
  3개 설정이 모두 채워졌고 허용 길이 안에 있는지 확인하고, 결과는 참/거짓만 공유한다.
- 팀장은 입력된 값이 실제 계좌와 같은지 대조한다(같은 문서 4단계).
- DB 자체에 장애가 있는 경우에는 Table Editor에서 수정하지 않고 1절의 현금 수기 운영으로 전환한다.
- 계좌 변경 중에는 신규 계좌이체 주문을 잠시 중단하고,
  기존 계좌로 송금 중이거나 입금 확인이 끝나지 않은 주문을 별도로 확인한다.

### 4.2 계좌 입력·확인 절차

계좌 입력 및 변경은 아래 문서를 따른다.

- [T-30 운영 계좌(송금 정보) 입력 절차](T-30-transfer-settings.md)

해당 문서를 기준으로 다음 역할을 구분한다.

1. 팀장(박수홍): 실제 계좌 값 1:1 전달, 입력된 값 대조
2. DB1(서동혁): 운영 계좌 값 입력·변경, 채움 확인 쿼리 실행
3. 확인 결과는 계좌 값이 아니라 `3개 모두 정상`·`대조 완료` 여부만 공유

입력 순서, 허용 값 규칙, 실제 Table Editor 조작 방법,
DB1 확인 쿼리는 위 문서를 기준으로 하며 이 매뉴얼에 별도로 복제하지 않는다.

### 4.3 변경 후 운영 검증 및 실패 대응

1. DB1의 채움 확인 결과와 팀장의 값 대조가 모두 끝났는지 확인한다.
2. 고객 화면에서 계좌이체 안내가 정상적으로 표시되는지 확인한다.
3. 기존 계좌로 이미 송금한 고객이 있는지 확인하고 중복 입금을 요구하지 않는다.
4. 정상 반영을 확인한 뒤 현장 책임자가 신규 계좌이체 주문 재개를 결정한다.
5. 오입력 또는 이상이 확인되면 신규 계좌이체 주문을 다시 중단하고,
   [T-30 운영 계좌 입력 절차](T-30-transfer-settings.md)에 따라 수정·재확인한다.

운영 기록에는 승인자 / 작업 시각 / 사유 / 변경 키 /
확인 성공 여부 / 고객 화면 확인 / 주문 재개 시각을 남긴다.
실제 은행명·계좌번호·예금주 값은 기록하지 않는다.
