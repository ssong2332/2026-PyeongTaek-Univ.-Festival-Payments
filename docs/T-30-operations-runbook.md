# T-30 현장 운영 폴백 매뉴얼

> 상태: QA 담당 작성 초안 (2026-09-29). 실제 운영 적용 전 현장 책임자·DB·배포 담당자 검수 및 2026-10-05 실기기 리허설 필요.
>
> 적용 범위: 2026-10-07~08 평택대학교 축제 부스, QR 주문·현금·계좌이체 운영.

## 1. 종이 메뉴판·현금 수기 주문

### 1.1 전환 조건 및 준비물

- 고객 QR 접속 불가, 주문 생성 실패, 관리자 대시보드 장애 등 정상적인 주문 처리가 어려우면 운영 책임자에게 즉시 보고한다.
- 온라인 접수 중단 및 수기 전환은 현장 책임자가 결정한다. 장애 발생·전환 시각과 마지막 정상 주문번호를 기록한다.
- 종이 메뉴판(확정된 가격), 수기 주문 기록지, 필기구, 현금 보관함·거스름돈, 임시 주문번호표, 조리 전달 전표를 준비한다.
- 고객에게 시스템 점검에 따른 **현금 수기 주문** 전환을 안내한다. 임의의 계좌번호·비공식 QR·송금 링크를 안내하지 않는다.

### 1.2 접수·조리·전달 절차

1. 메뉴·옵션·수량과 총금액을 고객과 확인한다.
2. 임시 번호를 `M-001`, `M-002`처럼 부여하여 온라인 픽업 번호와 구별한다. 이 번호 체계는 현장 책임자가 운영 전에 최종 승인한다.
3. 수기 기록지에 접수 시각, 임시 번호, 주문 상세, 총금액, 받은 현금, 거스름돈을 적는다.
4. 현금 수령을 확인한 뒤 고객에게 번호를 알려 주고 동일 번호를 적은 전표를 조리 담당자에게 전달한다.
5. 조리 완료 후 번호로 호출하고 전달 완료 시각을 기록한다.
6. 취소·환불 시 기존 기록을 지우지 않고 사유·반환 금액·담당자를 별도로 기록한다.

수기 기록의 기본 항목: 임시 주문번호 / 접수 시각 / 메뉴·옵션·수량 / 총금액 / 수령액 / 거스름돈 / 결제수단 / 상태(접수·조리중·전달완료·취소) / 담당자 / 비고. 고객의 이름·전화번호는 수집하지 않는다.

### 1.3 재고·매출과 복구 후 처리

- 수기 판매 수량 및 현금 매출은 온라인 데이터와 분리해 기록한다.
- 복구 직전 온라인에서 접수된 주문의 실제 저장·결제 여부를 먼저 대조한다. 오류 화면만 보고 주문 실패로 단정하거나 재생성하지 않는다.
- 수기 주문 사후 입력은 **T-28(2차)** 기능이 실제 구현·검증된 경우에만 사용한다. 미구현이라면 기록지를 보존하고 별도 정산한다.
- 온라인·수기 주문 및 재고·매출 중복 반영 여부를 운영 책임자와 함께 확인하고 정상 운영을 재개한다.

## 2. QR 코드 육안 점검 및 위변조 대응

- QR 인쇄물 하단에 T-25 배포 확인을 거친 **공식 접속 도메인**을 함께 인쇄한다. 임시 테스트 URL은 사용하지 않는다.
- 운영 시작 전, 담당자 교대 시, 운영 중 매시간(제안 주기), 이상 신고 즉시 점검한다. 최종 점검 주기는 현장 책임자가 확정한다.
- 인쇄물이 원위치에 있는지, 다른 스티커가 덧붙었거나 훼손되지 않았는지 확인한다.
- 스마트폰으로 QR을 인식해 표시되는 주소와 인쇄된 공식 URL을 비교하고 정상 주문 페이지 접속을 확인한다.
- 주소 불일치 또는 위변조 의심 시 해당 QR의 사용을 즉시 중단·가리고, 발견 시각과 인쇄물·연결 주소를 기록한 뒤 책임자에게 보고한다. 검증된 예비 인쇄물로 교체하고 두 명이 재확인한다.
- 의심스러운 페이지에 개인정보·관리자 계정 정보를 입력하지 않는다. 이미 해당 QR을 이용한 고객이 있다면 피해 여부를 확인할 수 있도록 별도 사고 기록을 남긴다.

점검 기록 항목: 점검 시각 / 담당자 / 인쇄물 상태 / URL 일치 여부 / 접속 결과 / 이상 및 조치 / 정상화 시각.

## 3. 서비스 장애 및 비상 연락 체계

### 3.1 장애 유형

고객 주문 화면 오류, 관리자 로그인·대시보드 오류, 현장 네트워크 장애, API·DB 오류, 입금 내역 확인 불가, QR 위변조 의심 등을 구분하여 기록한다. 연결 장애 시 가능하다면 모바일 데이터 등 다른 네트워크에서 접속을 비교한다.

### 3.2 대응 순서

1. **발견:** 발생 시각·증상·화면·마지막 정상 주문번호를 기록한다. 주문 확정 직후 오류가 났다면 동일 주문을 즉시 재접수하지 않는다.
2. **보고:** 현장 운영 책임자에게 알려 신규 온라인 주문의 일시 중단 및 수기 전환 여부를 결정받는다.
3. **진단:** 배포·백엔드 담당자가 Cloudflare Workers·API를, DB 담당자가 Supabase·주문 저장 여부를, 프론트엔드 담당자가 화면을 확인한다. QA 담당자는 재현과 복구 검증을 기록한다.
4. **폴백:** 장애가 지속되면 현장 책임자 승인 아래 1절의 현금 수기 주문으로 전환한다. 전환 시각을 공유한다.
5. **복구:** 고객 메뉴·주문 생성·관리자 수신·결제 확인·상태 변경을 점검하고 온라인/수기·결제 미확인 주문을 대조한 뒤 책임자 승인으로 재개한다.

### 3.3 연락 명단 — 운영 전 확정

| 순서 | 역할 | 책임 | 실제 담당자·연락 수단 |
|---|---|---|---|
| 1 | 현장 운영 책임자 및 대체 책임자 | 운영 중단·수기 전환·재개 결정 | 운영 전 입력 |
| 2 | 공동팀장 / QA | 사고 기록·복구 검증 | 운영 전 입력 |
| 3 | 백엔드·배포 담당 | API·Worker·배포 점검 | 운영 전 입력 |
| 4 | DB 담당 | Supabase·주문 저장 여부 확인 | 운영 전 입력 |
| 5 | 프론트엔드 담당 | 고객·관리자 화면 확인 | 운영 전 입력 |

전화번호와 개인 연락처는 공개 저장소에 커밋하지 말고 운영진만 접근할 수 있는 별도 연락망에 보관한다.

### 3.4 미확인 주문 및 사고 기록

- 결제 확인이 불가능하면 입금 확인·조리 시작으로 임의 전환하지 않는다. 은행 앱의 실제 입금 내역과 주문을 대조한다.
- 온라인 주문과 `M-` 수기 주문은 별개로 관리해 중복 조리·지급·재고 차감을 방지한다.
- 발생 시각 / 최초 발견자 / 장애 유형·증상 / 영향 범위 / 마지막 정상 주문번호 / 주문 중단·수기 전환 시각 / 연락·조치 내용 / 복구 검증 및 재개 시각 / 잔여 미확인 주문을 기록한다.

## 4. 관리자 설정 화면 장애 시 Supabase 폴백

### 4.1 적용 및 승인

- 기본 변경 경로는 T-52 관리자 설정 패널이다. 이 화면만 고장 났고 Supabase DB는 정상일 때 지정 담당자(DB1 또는 승인된 운영 담당자)만 **Supabase Table Editor**로 직접 수정한다.
- DB 자체 장애 시 직접 수정하지 않고 1절 현금 수기 운영으로 전환한다.
- 변경 전 현장 책임자의 승인을 받고, 공식 운영 프로젝트와 실제 계좌 소유자가 확인한 새 은행명·계좌번호·예금주를 재확인한다.
- 신규 계좌이체 주문을 잠시 중단하고, 기존 계좌로 송금 중이거나 확인되지 않은 주문을 별도로 확인한다.

### 4.2 실제 수정 경로

1. Supabase Dashboard에 로그인하고 운영 프로젝트가 맞는지 확인한다.
2. `Table Editor` → `public` → `app_settings`를 연다.
3. 아래 세 행의 `value`만 확인된 값으로 수정하고 저장한다. `key` 변경이나 다른 행의 삭제·초기화는 금지한다.

| key | 입력 내용 |
|---|---|
| `transfer.bank_name` | 실제 은행명 |
| `transfer.account_number` | 실제 계좌번호 |
| `transfer.account_holder` | 실제 예금주 |

- `transfer.*` 세 값이 모두 있어야 고객 송금 안내를 정상 설정된 상태로 표시한다.
- 행이 존재하지 않으면 임의로 다른 키를 만들지 말고 DB 담당자에게 확인한다.
- `app_settings`의 `updated_at`은 현재 스키마에서 자동 갱신 트리거 대상이 아니다. 수동 수정 시 DB 담당자가 변경 시각과 `updated_by` 처리 방식을 확인하고 별도 운영 기록에도 작업자를 남긴다.
- 실제 계좌번호, 인증키, 비밀번호를 GitHub·공개 Notion·단체 채팅·코드·커밋에 적지 않는다.

다른 설정값을 직접 편집할 경우에도 아래 **문자열** 형식을 지킨다. Table Editor는 애플리케이션 입력 검증을 우회한다.

| key | 허용 값 | 시드 기본값 |
|---|---|---|
| `payment.expire_minutes` | `1`~`120`의 정수 문자열 | `10` |
| `auto_complete.enabled` | `true` 또는 `false` | `false` |
| `auto_complete.minutes` | `1`~`120`의 정수 문자열 | `15` |

### 4.3 변경 검증 및 실패 시 처리

1. 저장된 3개 값을 재조회하여 두 명이 확인한다.
2. 새 고객 화면에서 은행명·계좌번호·예금주, 주문 금액, 계좌번호 복사 결과를 확인한다. 실제 입금 테스트는 계좌 소유자·운영 책임자의 사전 승인 하에서만 진행한다.
3. 기존 계좌로 송금한 고객을 확인하고 중복 입금을 요구하지 않는다.
4. 정상 반영을 확인한 뒤 책임자가 신규 계좌이체 주문 재개를 승인한다.
5. 오입력 시 즉시 신규 계좌이체 주문을 중단하고 DB 담당자에게 알려 검증된 이전 값으로 복구한 뒤 고객 화면을 재확인한다.

변경 기록: 승인자 / 작업자 / 시각 / 사유 / 변경 키 / 저장 성공 여부 / 고객 화면 확인 / 교차 검증자 / 주문 재개 시각. 실제 계좌번호 전체는 기록에 남기지 않는다.
