# T-15 관리자 주문 화면

사용자가 제공한 Figma `AdminView.tsx`를 바탕으로 T-15의 주문 조회·검색·확인 UI를 분리했다.
최신 `dev`의 T-15 백엔드(PR #37) 위에 UI 변경만 옮겼다.
#69의 주문 ID UUID 검증과 기존 라우트 시그니처를 유지한다.
API 처리 로직·DTO·Realtime 훅은 유지하고, 주문 목록 API의 날짜 생략 계약만 보완했다.

## 확인 방법

`npm ci` 후 `npm run dev -- --hostname 127.0.0.1 --port 3100`을 실행하고
`http://127.0.0.1:3100/dev/admin`을 연다. 개발 모드 전용이며 운영 빌드에서는 404다.
목업은 새로고침 버튼으로 초기화하며 서버 데이터에 접근하지 않는다.

- 데스크톱: 갈색 사이드바, 요약 카드, 주문 목록·상세 패널.
- 작은 화면: 단일 열 목록에서 주문을 선택하면 상세로 전환, 목록으로 복귀.
- 주문 확인은 `acknowledgedAt`만 반영하며 결제 확인이나 상태 전환을 하지 않는다.
- 미확인 강조는 기존 피드와 동일하게 pending/paid/cooking에 한정한다.
- 픽업 번호는 정확히 일치하는 오늘 주문을 먼저 찾고, 없으면 서버 검색을 요청한다.
- 로딩, 오류, 0건, 잘못된 번호, 확인 처리 실패를 구분한다.
- 상태는 실제 7개 enum을 사용하고 고객명·임의 로그인 계정·프론트 재고 복구는 이식하지 않았다.
- 목업 메뉴는 합의된 기본호떡 2000원 / 뿌링클 2500원 / 불닭 치즈 3500원 / 맛다시 4000원이다.

## 실제 서비스 연결

`LiveOrderDashboard`는 기존 `useOrdersFeed`로 목록·실시간 변경을 받고,
서버 검색 및 확인 응답을 DTO로 검증한다. 확인 성공 응답을 즉시 표시하며 비-2xx는 실패로 처리한다.
`GET /api/admin/orders`는 날짜가 없으면 KST 오늘 주문만 조회하고, 픽업 번호 검색은 날짜 조건을 무시한다.
주문 확인이 성공한 뒤 검색 결과 갱신만 실패하면 확인 성공을 유지하고 갱신 실패를 따로 안내한다.
T-13의 인증된 `/admin` 서버 페이지에 이 컴포넌트를 삽입해야 한다.
현재 로그인·라우트 보호가 없으므로 이 작업에서는 공개 `/admin` 페이지를 만들지 않았다.
T-18의 30초 sweep heartbeat는 #52가 병합된 뒤 별도로 연결한다.
T-16 결제·상태 변경 버튼, T-21 매출 집계, 메뉴·설정 화면은 별도 작업이다.

## 검증과 남은 항목

- 최신 `dev`(#71 포함) 기준 전체 단위 테스트 26개 파일, 272개 테스트 통과.
- UI 테스트: 확인 성공/실패, 결제 상태 유지, 검색 폴백, 늦은 검색 응답 무시,
  로딩·빈 화면, 잘못된 번호, 실제 어댑터의 확인 응답 및 401 처리.
- 브라우저: 1440px 목록·상세, 390px 상세·확인 동작 및 가로 넘침 없음 확인.
- 실제 Supabase 로그인·Realtime 3초 반영·RLS·운영 API 검증은 T-13과 기반 T-15 통합 후 수행한다.
- CI와 동일한 기본 `npm run build`, `npm run typecheck`, `npm run lint` 통과.
- 최신 `dev`(#69)의 주문 ID 검증을 보존하고, 기존 API 테스트로 인증 실패·조회 성공·404·확인 성공 동작을 재검증했다.
- KST 자정 경계의 날짜 기본값, 픽업 번호 날짜 무시, 확인 성공 후 검색 갱신 실패를 회귀 테스트로 확인한다.
- T-13의 보호된 `/admin` 페이지가 dev에 병합되면 `LiveOrderDashboard`를 연결하고 로그인·Realtime 동작을 검증한다.
