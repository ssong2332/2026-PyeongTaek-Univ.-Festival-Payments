# T-28 수기 주문 사후 입력 — 운영 연결

## 현재 구현

- 인증된 관리자 레이아웃 아래 `/admin/manual-orders`에서 종이 주문을 사후 입력한다.
- 메뉴·옵션·수량·결제수단·종이 주문 시각(KST)·종이의 M 번호를 입력한다.
- M 번호는 화면에서 `M-` 접두사를 고정하고 1~9999 숫자만 받는다. DB에는 숫자로 저장하며 화면·CSV에서는 `M-001` 형태로 표시한다.
- 저장은 `POST /api/admin/manual-orders` → `create_manual_order`(0104)로 연결되어 주문·항목·옵션·상태 이력·재고 차감을 한 DB 트랜잭션에서 처리한다.
- 같은 idempotency key 재요청은 같은 주문을 반환하고 재고·매출을 중복 반영하지 않는다. 실패 시 입력값과 key를 유지하고 성공 시 새 key를 발급한다.
- 같은 M 번호가 이미 있으면 DB가 `MANUAL_NUMBER_TAKEN`을 거부하고 화면은 입력값을 유지한 채 중복 안내를 표시한다.
- 재고 부족이어도 주문은 저장하며 재고는 0에서 멈춘다. 서버 응답의 `stockShortages`를 화면에 표시한다.
- 판매 종료 메뉴·비활성 옵션도 과거 종이 주문 재현을 위해 선택지에 남긴다. 비활성 옵션 그룹은 DB 0104 계약과 같이 최소 선택 수를 강제하지 않고 최대 선택 수는 유지한다.
- 관리자 주문 목록·상세에서는 고객 픽업 번호 대신 `M-001`과 `수기 입력`을 표시하며 주문 시각은 `manualOrderedAt`을 사용한다.
- T-21 통계, T-22 CSV, T-26 시간대 히트맵은 수기 주문에 대해 `manual_ordered_at` 기준을 사용한다.

## 검증

- 단위/UI 테스트: M 번호 범위, KST 변환, 옵션/재고 계산, 중복 저장 방지, 실패 시 입력·멱등키 유지, 실제 API 오류 envelope의 `MANUAL_NUMBER_TAKEN`, 비활성 옵션 그룹 사후 입력 계약을 검증한다.
- #137의 실제 Supabase 통합 테스트에서 0104 적용, 원자 저장, M 번호 중복·동시성, 고객 pickup 번호 비침범, 재고 부족, 통계·CSV 날짜 기준을 검증한다.
- #98 최신 head에서는 lint/test/build/worker build와 Supabase integration, T-18/T-19 sweep을 다시 수행한다.
