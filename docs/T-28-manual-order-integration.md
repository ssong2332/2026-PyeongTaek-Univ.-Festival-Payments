# T-28 수기 주문 사후 입력 — 화면 선작업

## 현재 구현

- 인증된 관리자 레이아웃 아래 `/admin/manual-orders`에 입력 화면을 두었다.
- 메뉴·옵션·수량·결제수단·종이 주문 시각(KST)을 입력하고 예상 금액 및 현재 재고 부족을 확인할 수 있다.
- 필수값, 옵션 선택 범위, 날짜 유효성, 미래 시각을 검사한다. 저장 중 중복 클릭을 막고 실패 시 입력값과 멱등키를 유지한다.
- 현재 메뉴는 `GET /api/menu?lang=ko`로 읽는다. 이 API는 활성 메뉴만 제공하므로 장애 당시 판매했지만 이후 비활성화된 메뉴는 목록에 없을 수 있다.
- 저장 API와 원자적 DB 함수가 아직 없으므로 실제 화면의 저장 버튼은 **비활성화**되어 있다. 이 상태를 T-28 완료 또는 운영 사용 가능으로 취급하지 않는다.

## 연결 시 필요한 계약

1. T-20 관리자 메뉴 조회가 준비되면 이 화면의 메뉴 소스를 교체하고, 장애 당시 메뉴를 선택할 수 있는지 검증한다.
2. 인증된 `POST /api/admin/manual-orders`가 `ManualOrderRequestSchema` 입력을 받는다. 요청 가격을 신뢰하지 않고 DB의 메뉴·옵션 가격으로 주문 항목 스냅샷을 생성한다. 실제 저장은 하나의 DB 트랜잭션에서 완료 상태 주문, `source='manual'`, `manual_ordered_at`, 상태 이력, 재고 차감을 처리한다.
3. `idempotencyKey` 재요청은 같은 주문을 돌려줘야 한다. 네트워크 오류 후 재시도에서 주문·재고·매출이 중복되면 안 된다.
4. 기존 `orders.stock >= 0` 제약과 PRD의 “재고 부족 경고 후 저장 허용”은 충돌할 수 있다. 부족 수량 기록 및 재고 처리 정책을 팀장과 확정한 뒤 DB 함수에 반영한다. 화면은 경고를 표시한다.
5. T-21 `get_stats`는 현재 `orders.created_at`으로 날짜를 나눈다. 수기 주문의 매출을 종이 주문 날짜에 반영하려면 `manual_ordered_at` 기준으로 집계하거나 저장 시 `created_at` 정책을 명시해야 한다. 동일 조건의 CSV(T-22)도 맞춘다.
6. 저장 성공 후 관리자 주문 목록에 “수기 입력” 출처가 보이고, 현금·계좌이체 완료 주문 각각 매출·재고·상태 이력이 일치하는지 실제 PostgreSQL로 확인한다.

DB 마이그레이션 번호는 운영 적용 순서(0017 → 0018 → 0019)를 확인해 확정한다. 현재 브랜치는 기존 마이그레이션을 수정하지 않는다.
