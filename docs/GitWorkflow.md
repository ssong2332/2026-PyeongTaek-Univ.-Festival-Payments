# GitWorkflow — 2026-PyeongTaek-Univ.-Festival-Payments

> 모든 팀원은 이 규칙대로만 커밋한다.

## 금지

- dev·main 브랜치 직접 커밋 금지. 예외 없음 — PR 또는 검증 후 병합만 허용.
- force push 금지 (팀장이 명시 요청한 경우만 예외).
- 합의되지 않은 커밋·푸시 금지.

## 병렬 작업과 브랜치 격리

팀원들이 동시에 병렬 작업을 진행할 때는 상호 충돌을 방지하기 위해 반드시 작업 단위로 분리된 브랜치(`feat/T-xx-설명`)에서 작업하며, 동일 파일(특히 `src/infra`, `app_settings` 관련 컴포넌트 등)을 동시에 수정하지 않도록 격리 규칙을 준수한다.

## 브랜치 전략

| 브랜치 | 용도 | 규칙 |
|---|---|---|
| main | 항상 동작하는 상태 | 병합으로만 갱신 (PR 또는 팀장의 승인 후 병합) — 직접 커밋 금지 |
| dev | **배포 기준 브랜치**(2026-09-23 — Vercel이 `dev`를 실제 서비스 주소로 배포). 작업 브랜치는 여기로 PR | 병합으로만 갱신 (PR + CI 통과) — 직접 커밋 금지. 병합 즉시 QR 주소에 반영되므로 DoD 통과 후에만 병합 |
| feat/{작업ID}-{설명} | 기능 구현 | Tasks.md의 ID 사용 (예: feat/T-01-harness) |
| fix/{설명} | 버그 수정 | |

최신 `dev`에서 기능 브랜치를 만들고 PR의 대상(base)은 `dev`로 지정한다. `main`은 최종 반영 시에만 사용한다.

`git checkout -b feat/T-xx-...`로 브랜치를 전환한 후 작업을 진행하고, 커밋(`git commit`)을 수행한다.

## 커밋 메시지 (Conventional Commits)

```
{type}: {한 줄 요약}
```

| type | 용도 |
|---|---|
| feat | 기능 추가 |
| fix | 버그 수정 |
| docs | 문서만 변경 |
| refactor | 동작 불변 구조 변경 |
| test | 테스트만 변경 |
| chore | 빌드·설정 등 그 외 |

## 병합 조건

- [ ] DefinitionOfDone.md 전부 통과
- [ ] CI(GitHub Actions) 통과 (단위 테스트, 빌드 등)
- [ ] 코드 리뷰 통과 및 팀장 최종 승인

병합 수행 주체는 팀장이다.
