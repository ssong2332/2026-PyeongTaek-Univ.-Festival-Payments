# 교대 재고 사진 운영 정책 (PR #158)

## 보존·접근 정책

- 사진은 비공개 `inventory-photos` Storage 버킷에 보관한다. 관리자 API만 메타데이터와 1시간 유효 서명 URL을 제공한다.
- 파일당 최대 5 MiB이며 JPEG, PNG, WebP만 허용한다. 서버는 MIME과 파일 헤더를 확인하고, 기존 버킷의 비공개·크기·MIME 설정이 다르면 업로드를 거부한다.
- 촬영 시각으로부터 30일이 지난 사진은 자동으로 삭제하지 않는다. 관리자가 교대 화면의 **30일 지난 사진 정리**를 눌러 수동으로 삭제한다. 삭제된 파일은 복구할 수 없으므로 실행 전에 화면에서 확인한다.
- 업로드 전에 `inventory_photo_uploads`에 경로와 업로드 관리자 ID를 기록한다. 업로드·메타데이터 저장·보상 삭제 중 오류가 나도 남은 기록을 통해 파일을 재확인할 수 있다. 관리자 정리는 생성 후 24시간이 지난 의도 기록만 재처리한다. `inventory_photos.storage_path`에 참조가 있으면 파일은 보존하고 의도 기록만 지운다. 참조가 없을 때에만 Storage 파일을 제거한다. 한 번에 최대 100건이므로 남은 기록이 있으면 정리를 반복한다.

## 감사·삭제 책임

- 촬영자 이름, 촬영 시각, 업로드 관리자 ID, Storage 경로는 `inventory_photos`에 남는다. 업로드 중단 건의 관리자 ID와 경로는 `inventory_photo_uploads`에 남는다. 이 두 테이블은 service role만 접근한다.
- 정리 실행은 로그인한 관리자가 담당한다. API는 `inventory.photos.manual_cleanup` 로그에 실행 관리자 ID, 만료 사진 삭제 수, 미참조 파일 삭제 수, 실패 수를 기록한다. 보상 삭제 실패는 `inventory.photos.compensation_failed`, 재정리 실패는 `inventory.photos.orphan_reconciliation_failed`로 기록한다. 경로 전체나 파일 내용은 로그에 남기지 않는다.
- 운영 책임자는 정리 실행 시각·담당자·사유·삭제/실패 건수와 재시도 결과를 운영 기록에 남긴다. 실패가 있으면 서버 로그와 `inventory_photo_uploads` 잔여 건수를 확인하고 Storage·DB 장애가 해소된 후 관리자 정리를 다시 실행한다. 개별 Storage 파일을 수동 삭제하기 전에는 DB 참조 여부를 확인한다.

## 배포 게이트

1. T-54의 `0106`과 T-55의 `0107` DB PR이 먼저 `dev`에 병합되어야 한다.
2. 격리 DB에서 `0106 → 0107 → 0108_inventory_photos.sql`을 순서대로 적용하고 통합 테스트를 통과시킨다. 현재 `0105 → 0108` CI 성공은 이 게이트의 증거가 아니다.
3. 운영 DB는 별도 승인 후 DB1이 선행 마이그레이션을 확인·적용하고, 그 다음 `0108`을 적용한다. 이후 앱을 배포하고 비공개 버킷 설정과 업로드·서명 URL·정리를 검증한다.

이 문서는 PR 구현 정책이다. PR 병합이나 운영 DB·Storage 변경을 승인한 기록으로 사용하지 않는다.
