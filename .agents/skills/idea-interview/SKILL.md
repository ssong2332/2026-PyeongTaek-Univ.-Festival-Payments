# 아이디어 인터뷰 (파이프라인 0단계)

Claude Code·Codex·안티그래비티 공통 절차다. **사용자와 직접 대화하는 세션이 수행한다** — 서브에이전트는 질문 후 대기할 수 없으므로 이 절차를 위임하지 않는다.

목적: 사용자가 아이디어를 여러 각도에서 다듬게 돕는 것. 받아 적는 것이 아니라 **같이 설계하는 대화**다.

## 금지 (다른 모든 규칙보다 우선)

- 사용자가 완성을 선언하기 전에 인터뷰를 끝내는 것 금지. 커버리지 표가 다 찼어도 임의 종료 금지.
- **아이디어가 상세하다는 이유로 질문을 생략하는 것 금지.** 아무리 자세히 설명받아도 커버리지 표의 빈칸은 전부 질문으로 채운다.
- 사용자가 말하지 않은 것을 명세에 넣는 것 금지. 추론한 내용은 "이렇게 이해했는데 맞습니까?"로 확인받는다.
- 추천만 제시하고 대안을 숨기는 것 금지 — 항상 반대 방향을 함께 준다.
- 한 라운드에 5개 이상 질문 금지 (2~4개). 사용자를 지치게 하면 답이 부실해진다.
- **아이디어 본문을 선택지로 묻는 것 금지.** "무엇을 만들고 싶은가"는 반드시 자유 서술로 받는다 (선택지로 물으면 "직접 입력"을 골라도 내용이 안 와 한 라운드가 버려진다). 선택지는 사실상 답이 정해진 항목(개인/팀, 스택, 배포 등)에만 쓴다.
- 이미 답변받은 것을 다시 묻는 것 금지. 바뀔 여지가 있으면 "확정된 것" 요약에서 보여주고 수정 기회만 준다.
- 진행 방식(정식 파이프라인/vibe 모드)을 사용자 확인 없이 임의로 정하는 것 금지 — 추천은 하되 최종 선택은 사용자가 한다.

## 진행 방식 추천 (커버리지 인터뷰 시작 전, 1회만)

사용자가 아이디어를 자유 서술로 말하면, 커버리지 표로 들어가기 전에 이것부터 한다: 정식 파이프라인(6-에이전트, 승인 게이트 2단계)과 vibe 모드(`.agents/skills/vibe-mode/SKILL.md`, 서브에이전트 없이 승인 대기 없이 빠르게) 중 어느 쪽이 이 아이디어에 나을지 판단해 추천하고, 왜 그런지 설명한다. **사용자가 이미 방식을 말했으면**("vibe로 진행해" 등) 이 단계를 건너뛰고 그 방식으로 바로 시작한다.

| 신호 | 추천 |
|---|---|
| 개인 + 기간이 며칠 이내 + 기능 범위가 단순(CRUD 수준) | vibe 모드 — 목적이 학습·프로토타입·토이·데모든, 개인이 계속 쓸 실사용 도구든 상관없다. "개인이 계속 쓴다"는 것 자체는 정식 파이프라인 신호가 아니다 — 다른 사람도 쓰는지가 갈림점이다 |
| 협업자·팀이 있음 | 정식 파이프라인 |
| 다른 사람도 쓰는 공유 릴리스·프로덕션 배포 | 정식 파이프라인 |
| 개인정보·결제·인증 등 민감 데이터를 다룸 | 정식 파이프라인 (급한 사정이 있으면 "vibe 모드 + security-audit 스킬 병행"을 대안으로 제시) |
| 개인 + 계속 쓸 실사용 도구지만 기능 범위가 복잡(여러 화면·외부 연동·동기화 등) | 더 신중한 쪽(정식 파이프라인)을 추천하되, vibe 모드를 대안으로 함께 제시하고 트레이드오프를 짧게 설명 |
| 표의 어느 행에도 안 맞음 | 임의로 정하지 말고 사용자에게 직접 물어본다 |

추천 형식은 아래 "추천·반대 제시 규칙"과 같다 — 추천 하나, 대안(반대 방향) 하나, 그 방향을 고를 이유. 판단 근거는 이 단계에서 사용자가 말한 것(개인/팀 여부, 목적, 기간 등 — 커버리지 항목 1의 내용)에서 가져온다. 아직 안 나온 판단 근거가 있으면 이 단계에서 짧게 물어봐도 된다 — 어차피 커버리지 항목 1과 겹치므로 뒤에서 다시 묻지 않는다.

- **정식 파이프라인으로 확정** → 아래 "라운드 절차"로 계속한다. 이 단계에서 이미 나온 항목 1 답변은 재사용하고 다시 묻지 않는다.
- **vibe 모드로 확정** → `.agents/skills/vibe-mode/SKILL.md`로 넘어간다. 이미 받은 아이디어 자유 서술은 그 스킬의 인터뷰 1번 항목으로 재사용한다 — 처음부터 다시 묻지 않는다.

## 종료 조건

**사용자가 명시적으로 완성을 선언할 때만 끝난다** ("이제 됐어", "완성됐다", "이대로 진행해" 등).

| 상황 | 행동 |
|---|---|
| 커버리지 다 참 + 사용자 미선언 | 계속한다. 남은 것은 심화 질문(엣지 케이스, 실패 시나리오, 확장 방향)으로 |
| 커버리지 빈칸 있음 + 사용자가 진행 선언 | 즉시 종료. 남은 빈칸은 "미정"으로 표시해 PRD의 Open Questions로 넘긴다 |
| 사용자가 답을 모르겠다고 함 | 추천·반대와 함께 판단 근거를 더 주고, 그래도 미정이면 "미정"으로 두고 다음 항목으로 |

## 라운드 절차 (반복)

1. **현재 상태 요약** (2회차부터): 확정된 것 / 남은 빈칸을 표로 짧게 보여주고, **"확정 n건 · 남은 빈칸 n개 · 예상 n라운드"를 한 줄로 명시한다** (한 라운드당 2~4개 기준으로 산정). 끝이 보여야 사용자가 지치지 않는다. 심화 질문 단계에 들어가면 "커버리지 완료 — 이후는 선택적 심화"라고 밝힌다.
2. 커버리지 표에서 **가장 결정적인 빈칸 2~4개**를 고른다 (위 항목이 아래 항목의 답을 바꾸므로 번호 순서를 지킨다).
3. 각 질문을 **추천·반대 형식**(아래)으로 제시한다.
4. 답변을 확정 항목에 반영한다. 그 답이 이미 확정된 다른 항목을 흔들면 그 영향을 알리고 재확인한다.
5. 사용자가 완성을 선언할 때까지 1로 돌아간다.

질문 방식은 도구에 맞춘다: 선택지 UI(구조화 질문 도구)가 있으면 그것을 쓰고, 없으면 번호 매긴 마크다운 질문으로 묻고 답을 기다린다. 어느 쪽이든 **"직접 입력"의 여지를 항상 남긴다**.

## 커버리지 표 (빈칸을 질문으로 채운다)

우선순위 순. 상위가 하위를 결정하므로 위에서부터 묻는다.

| # | 항목 | 확인할 것 |
|---|---|---|
| 1 | 프로젝트 성격 | 개인/팀(팀이면 인원·역할 분담·협업 방식), 목적(과제·포트폴리오·실사용·학습), 기간·마감 |
| 2 | 사용자와 문제 | 주 사용자는 누구, 어떤 상황에서, 무슨 문제를 겪는가, 지금은 어떻게 해결하는가 |
| 3 | 핵심 가치 | 기존 방법·경쟁 서비스와 무엇이 다른가. 그 차이가 사용자에게 왜 중요한가 |
| 4 | 기능 범위 | MVP 필수 기능, 있으면 좋은 기능, **명시적으로 안 할 것**(범위 제외) |
| 5 | 성공 기준 | 무엇이 측정·시연되면 성공인가 (가능하면 수치) |
| 6 | 언어·스택 | 프로그래밍 언어, 프레임워크, 선택 이유(익숙함·요구사항·학습 목적) |
| 7 | 데이터 | 저장할 데이터의 종류·양, DB 필요 여부와 종류, 외부 API·데이터 출처 |
| 8 | 인증·권한 | 로그인 필요 여부, 방식(자체·OAuth), 사용자 권한 구분 |
| 9 | 배포·운영 | 배포 대상(로컬·Vercel·클라우드·스토어), 도메인, CI 사용 여부, 비용 한도 |
| 10 | 제약·기존 자산 | 반드시 써야 하는 기술(수업·회사 요구), 재사용할 코드·디자인, 금지 사항 |
| 11 | 품질 기준 | 테스트 범위, 보안 수준(개인정보·결제 여부), 접근성·다국어 필요 여부 |
| 12 | 화면 (UI 있는 프로젝트만) | 어떤 화면들이 있고 각각에서 사용자가 무엇을 끝내는가. 참고할 서비스·디자인 방향이 있는가. UI가 없으면 "해당 없음"으로 즉시 넘어간다 |

## 추천·반대 제시 규칙

선택형 질문은 이 형식을 지킨다.

- **추천**: {안} — {이 프로젝트 조건에서 유리한 이유}
- **반대 방향**: {대안} — {이게 나은 조건과 감수할 것}
- 두 방향의 차이가 이 프로젝트에서 의미 없으면 그렇다고 말하고 하나를 정해준다 (고민 낭비 방지).

추천은 **앞선 답변에 근거**해야 한다. 근거 없이 유행하는 스택을 밀지 않는다.

예시:

> **데이터베이스를 뭘로 할까요?**
> - 추천: PostgreSQL — 관계형 데이터에 안전하고, 무료 티어 호스팅(Supabase·Neon)이 있어 개인 프로젝트도 배포까지 갑니다.
> - 반대 방향: SQLite — 파일 하나라 설정·백업이 단순하고 로컬 개발이 빠릅니다. 대신 동시 쓰기가 많거나 인스턴스를 늘리면 한계가 옵니다.
> - 앞서 "혼자 쓰는 도구"라고 하셨으니 SQLite로도 충분합니다. 나중에 공개하실 생각이면 지금 전자를 택하는 게 이전 비용을 아낍니다.

기능 논의에서도 같은 원리를 쓴다: 사용자가 기능을 말하면 **빼는 방향**(MVP 축소)과 **넓히는 방향**(인접 기능)을 모두 제시해 범위 감각을 만든다.

**기능 선택은 개수를 제한하지 않는다** — 필요한 것을 전부 고를 수 있게 복수 선택을 열어둔다. 대신 고른 합이 기간을 넘기면 그 자리에서 **기능별 예상 소요를 표로 제시하고** 1차/2차 분할·기간 연장·축소 세 방향을 선택지로 준다. 고르기 전에 제한을 거는 것보다, 고른 뒤 사실을 보여주고 사용자가 재조정하게 하는 편이 아이디어를 덜 깎는다.

## 인터뷰 종료 후

1. **최종 명세 요약**을 표로 제시한다 (커버리지 12항목 + 미정 항목 명시).
2. **조합 위험 점검**: 개별 답은 멀쩡한데 둘이 겹치면 문제가 되는 조합을 한 번 훑는다 (예: "로그인 없음" + "공개 URL 배포", "실시간 동기화" + "서버리스 무료 티어", "1~2주" + "새 기술 학습"). 커버리지 표는 항목을 하나씩 보므로 이 결합을 놓친다. 발견하면 사용자에게 알리고 해소 방향을 제시한다.
3. 사용자 확인을 받는다.
4. **사용자 답변을 원문 그대로 인용해** 기획 단계를 시작한다 — 요약·의역해서 넘기지 않는다. 넘기는 쪽의 해석이 섞이면 받는 쪽은 그것이 사용자의 말인지 구별할 수 없다 — 서브에이전트를 쓰는 도구는 planner를 호출하고, 없는 도구는 planner 역할 규칙(AGENTS.md 소유권·절차)에 따라 이어서 수행한다.
5. 미정 항목은 docs/PRD.md의 Open Questions 표로 넘긴다.
