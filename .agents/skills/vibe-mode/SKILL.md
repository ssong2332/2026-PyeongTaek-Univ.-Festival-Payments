# vibe 모드 (파이프라인 우회 경로)

정식 파이프라인은 팀·공유 릴리스를 전제로 승인 게이트를 둔다. 혼자 빠르게 감으로 만들어보고 싶을 때는 그 게이트 자체가 걸림돌이다 — 이 스킬은 AGENTS.md의 6-에이전트 파이프라인을 고치지 않고 **완전히 별도 경로로 우회**한다. AGENTS.md·에이전트 정의는 이 스킬이 켜져 있어도 그대로다 — 다음에 정식 파이프라인이 필요한 프로젝트를 하면 아무 조건 없이 원래대로 쓴다.

## 언제 쓰는가

두 경로로 들어온다. 어느 쪽이든 **최종 선택은 사용자가 확정**한다 — 프로젝트 성격만 보고 메인 세션이 임의로 이 경로를 고르지 않는다(잘못 고르면 나중에 되돌리기 어렵다).

1. **아이디어 인터뷰에서 추천받아 확정**: `idea-interview/SKILL.md`의 "진행 방식 추천" 단계가 프로젝트 성격(개인/팀, 목적, 기간)을 보고 이 경로를 추천했고, 사용자가 그 추천을 받아들인 경우. 이미 답한 아이디어 자유 서술을 재사용한다 — 아래 1단계 인터뷰의 항목 1을 다시 묻지 않는다.
2. **진행 중 사용자가 명시적으로 전환 요청**: "vibe로 진행해" / "vibe 코딩으로" / "라이트하게 가자" / "가볍게 만들어보자" / "빠르게 프로토타입만" / "감으로 만들어보자" 같은 문구.

## 금지

- 정식 파이프라인 문서(docs/PRD.md 등)의 구조 자체를 바꾸지 않는다 — 같은 파일에 더 짧게 쓸 뿐, 새 문서 형식을 만들지 않는다.
- planner·architect·reviewer·quality-assurance 서브에이전트를 호출하지 않는다 — 메인 세션이 직접 쓰고 직접 확인한다.
- Red-Green-Refactor와 화면 실물 확인은 생략하지 않는다 — 이 둘은 무게가 아니라 실제로 결함을 잡아주는 것들이다(AGENTS.md 검증 루프).
- 이 경로로 시작한 프로젝트가 커져서 팀 협업·공유 릴리스가 필요해지면, 그 시점에 정식 파이프라인으로 전환할지 사용자에게 물어본다 — 계속 vibe로 미는 것을 기본값으로 삼지 않는다.

## 1단계 — 짧은 인터뷰

아래 5항목만 묻는다. 자유 서술(1번)과 선택형(2~5번)을 섞어 쓰고, 선택형은 추천안을 한 줄로 붙인다(반대 방향까지 다 늘어놓지 않아도 된다 — 속도가 이 경로의 목적이다). **최대 2라운드.** "알아서 정해줘"는 정식 답변이며, 이 경로에서는 오히려 기본값에 가깝다.

| # | 항목 | 확인할 것 |
|---|---|---|
| 1 | 무엇을 만들 것인가 | 자유 서술로만 받는다 (idea-interview와 동일 이유) |
| 2 | 언어·스택 | 언어/프레임워크, 짧은 이유 |
| 3 | MVP 기능 범위 | 지금 당장 필요한 것만 — 있으면 좋은 기능은 생략 |
| 4 | 데이터·인증 | DB 필요 여부, 로그인 필요 여부 (해당 없으면 바로 넘어감) |
| 5 | 배포 | 로컬 실행만인지, 배포까지 볼지 |

## 2단계 — 문서를 메인 세션이 직접 쓴다

인터뷰 직후 같은 세션에서 정식 파이프라인과 **같은 문서**(`docs/PRD.md`, `docs/Tasks.md`, `docs/DECISIONS.md`)에 쓴다 — 다만 훨씬 짧게: PRD는 "한 줄 정의"와 "기능 요구사항"(F-xx, 승인 기준 한 줄)만 채우고, "사용자"·"핵심 가치"·"성공 기준" 같은 나머지 절은 "vibe 모드 — 생략"이라고 명시해 빈칸으로 남기지 않는다. "화면" 절은 UI가 있으면 표를 채우고(정식 파이프라인과 동일 — 이건 무게가 아니라 실제로 값을 하는 절이다), 없으면 "해당 없음"만 쓴다. 언어·스택 선택은 PRD가 아니라 `docs/DECISIONS.md`에 한 줄로 남긴다(우리 PRD 템플릿엔 별도 스택 절이 없다 — 있는 절만 쓴다). Architecture.md는 만들지 않는다 — 정말 설계가 필요할 만큼 커지면 vibe 모드를 벗어날 시점이다.

PRD 머리글 "상태"는 이 경로에서는 게이트가 아니므로 건드리지 않는다 — 정식 승인 절차를 흉내 내지 않는다.

## 3단계 — 빌드 루프 (태스크마다 반복)

1. **구현** — 메인 세션이 직접 코드를 쓴다. 새 기능·버그 수정 모두 Red-Green-Refactor: 실패하는 테스트부터 → 실패 확인 → 최소 구현으로 통과 → 리팩토링.
2. **실물 확인** — 화면이 있는 변경이면 실제로 띄워 본다. Claude Code는 Browser pane 도구(`mcp__Claude_Browser__*`)로 직접, 그 도구가 없으면 실행 결과를 직접 확인한다. 테스트가 전부 초록이어도 이 단계를 건너뛰지 않는다(AGENTS.md와 같은 이유 — 번들러 전용 에러는 테스트 러너가 못 본다).
3. **done 판정** — 아래를 전부 충족해야 `docs/Tasks.md` 상태를 `done`으로 바꾼다. 하나라도 안 됐으면 계속 `진행`.
   - 새로 추가한 테스트가 실패하는 것을 먼저 확인한 뒤 통과시켰다 (red 출력 확보).
   - 테스트 실행 출력을 확보했다 — "통과했다"는 진술만으로는 미충족.
   - 화면이 있는 변경이면 2단계의 실물 확인 결과를 확보했다.
   - 이번 태스크 범위 밖 파일이 `git diff`에 없다.

## 4단계 — 커밋

브랜치 전략은 정식 파이프라인과 같다 — main 직접 커밋은 여기서도 금지고, 훅이 물리 차단한다(대화 맥락을 아는 예외가 아니다). 줄어드는 건 승인 대기뿐이다: 태스크 브랜치를 만들고, 구현·done 판정까지 마쳤으면 리뷰·QA 승인을 기다리지 않고 바로 병합한다(GitWorkflow.md "vibe 모드에서의 브랜치" 참조). 커밋 메시지 형식(Conventional Commits)은 그대로 따른다. 사용자 요청 없는 커밋·푸시는 여전히 금지.

## 종료 (정식 파이프라인으로 전환)

다음 중 하나가 되면 계속 vibe로 밀지 말고 사용자에게 정식 파이프라인 전환 여부를 물어본다:
- 협업자가 생겼다.
- 공유 릴리스·프로덕션 배포가 필요해졌다.
- 설계 결정이 서로 얽혀서 한 줄 DECISIONS로는 감당이 안 된다.

전환하기로 하면, 지금까지 쓴 PRD.md·Tasks.md·DECISIONS.md를 그대로 기반 삼아 architect부터 정식으로 호출한다 — 처음부터 다시 인터뷰하지 않는다.
